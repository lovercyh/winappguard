## 阶段 4：规则管理页（恢复联网的入口）

> 本阶段**起因是一个真实 bug**：用户用 Chrome 测试时，阻止联网后 Chrome 从连接列表里消失了，
> 导致无法恢复联网。根因是把「恢复入口」挂在了**实时连接**上，而拦截恰好会消灭实时连接 ——
> 拦截越成功越无法恢复。修复方式是把恢复入口改为挂在**持久化的防火墙规则**上。

### 恢复路径（核心）

| # | 操作 | 预期 |
|---|---|---|
| 4.1 | 阻止某个程序联网（如 Chrome） | 规则创建成功 |
| 4.2 | 观察「联网连接」页 | 该程序**消失或只剩零星行**（它连不上，自然没有连接）—— 这是正常现象 |
| 4.3 | 切到「黑名单」页 | **该程序一定在这里**，显示程序名、完整路径、动作、规则名 |
| 4.4 | 标签页标题 | 显示「规则（N）」，N 是**当前规则总数**（阻止 + 允许） |
| 4.5 | 页顶的橙色说明 | 必须明确写出「被阻止的程序不会出现在联网连接页里」及恢复方法 |
| 4.6 | 选中它 → 点「解除阻止（允许联网）」 | 弹确认框，列出将删除的规则名 |
| 4.7 | 确认 | 规则被删除，该程序恢复联网；连接页重新扫描后能看到它 |
| 4.8 | **极端场景**：阻止一个程序后重启电脑，程序完全不在运行 | 该程序的规则**仍在列表里**，随时可以恢复 |

### 选中状态机（这块出过两次问题，是重点）

> 背景：DataGridView 会在数据绑定后、以及**标签页重新显示时**自己把第一行设为当前行，
> 而 `CurrentCell = null` 挡不住切标签页。所以「当前行」不等于「用户选中」。

| # | 操作 | 预期 |
|---|---|---|
| 4.17 | 启动后不做任何操作 | 连接表无当前行，「阻止」「允许」都是灰的 |
| 4.18 | **切到规则页再切回连接页** | 连接表仍无当前行，按钮仍为灰（这条曾失效过） |
| 4.19 | 点击某一行 | 按钮按状态启用，提示显示程序名/连接数/当前状态 |
| 4.20 | 开启自动刷新，点击一行后等 30 秒 | **选中保持**，按钮保持可用 |
| 4.21 | 让被选中的连接消失（关掉该程序） | 选中被放弃，按钮变灰，**不落到第一行** |
| 4.22 | 规则页启动时 | 不自动选中任何规则，「允许」「删除选中」都是灰的 |
| 4.23 | 规则页点击一条规则，切走再切回 | **用户的选中保持** |
| 4.24 | 表格里高亮着一行但没被点击过 | 提示写「点击一行来选择要操作的程序」，说明按钮为什么是灰的 |

### 崩溃回归（实测发现的越界崩溃）

> 起因：连接数从 100 条掉到 50 条时，表格里还挂着索引 90 的旧行，
> 此时去读当前行的数据会抛 `IndexOutOfRangeException`，整个程序崩掉。
> 修复：**先抓取选中项，再替换数据列表**，顺序不能反。

| # | 操作 | 预期 |
|---|---|---|
| 4.25 | 100 条连接时选中靠后的行，等程序大量退出后再刷新 | **不崩溃**，选中被合理放弃 |
| 4.26 | 自动刷新连续跑 30 分钟（连接数反复增减） | 不崩溃、无异常弹窗 |
| 4.27 | 删除规则后连接列表重建 | 不崩溃 |

## 单实例（补充：用户报的 bug）

> **bug 现象**：启动程序后再双击一次 exe，托盘里出现**两个一模一样的图标**。
>
> **根因**：程序没有做单实例控制，第二次双击会真的启动第二个进程。
>
> 这不只是「难看」——**两个实例会同时操作防火墙和计划任务**，操作可能互相打架，
> 而且用户搞不清该关哪一个。我在阶段 6 的验收清单里写过「不会出现两个托盘图标」，
> 但当时只依赖了计划任务的 `IgnoreNew` 策略 —— 那只管计划任务触发的启动，
> **管不住用户手动双击**，等于那条验收项根本没有实现。
>
> **修复**：命名互斥体 + 自定义窗口消息广播。第二个实例被拦下后，
> 广播一条消息请已有实例把主窗口显示出来，然后自己安静退出 ——
> 用户点两下的效果就是「窗口回到前台」。

## 关键结论记录

- **路径解析率**：管理员下 93%（170/181），非管理员下 71%。失败的只有 Windows 内核 `System` 进程和采样瞬间退出的进程，属于正常现象。
- **默认视图条数**：本机约 90~110 条；放开全部过滤后约 200 条（不含回环）/ 490 条（含回环）。
- **架构决定**：只使用 Win32 API 查询进程路径，不创建 `System.Diagnostics.Process` 对象，避免长时间自动刷新导致句柄泄漏。
- **进程路径解析率实测**：管理员 93%。这证明了阶段 0 把 `requireAdministrator` 写进 manifest 是必需的。
- **默认出站动作实测为「允许」**：因此「允许某程序联网」的正确实现是**删除阻止规则**，
  而不是创建允许规则 —— Windows 防火墙里阻止规则优先级高于允许规则，同时存在时阻止生效。
- **安全护栏位置**：全部做在 `FirewallManager` 内部，不在界面层。界面层的置灰只是体验优化，不是安全边界。
- **【重要修正】防火墙对「已建立的连接」的实际效果**：
  我原先按标准文档推断「防火墙只对新建连接生效，已建立的连接不受影响」，并把这个说法写进了确认框。
  **实测推翻了它**：在浏览器处于联网状态时点「阻止联网」，浏览器**立刻掉线**。
  由于我无法区分「防火墙切断了已有连接」和「浏览器检测到新请求失败后主动断开」这两种机制，
  确认框文案已改为按**实测现象**描述（「当前正在进行中的连接也会马上断开」），
  并附一句「如果发现它仍能联网，重启该程序再试一次」，不再向用户断言底层机制。
  如需彻底弄清楚机制，可用一个不主动断线的长连接场景复测（例如大文件下载中途阻止、SSH 会话中途阻止）。
- **回车键行为（确认框）**：`ConfirmForm` 没有设置 `AcceptButton`，但按回车**会确认**。
  实测中 `Form.ProcessDialogKey(Enter)` 返回 True（窗体层声称已处理），而按钮仍被触发，两条证据互相矛盾，
  说明该行为依赖 WinForms 内部实现细节。产品负责人已确认**保留**此行为（符合 Windows 用户普遍预期），
  因此代码中保留了说明注释，未做拦截。
- **DataGridView 的「当前行」不等于「用户选中」**：它会在数据绑定后、以及**标签页重新显示时**自动把第一行设为当前行，
  `CurrentCell = null` 挡不住切标签页。因此界面用独立的 `SelectionConfirmed` 标志来判断「用户到底点没点过」，
  操作按钮只认这个标志。这是实测踩出来的，不是设计上的想当然。
- **「桌面程序点击关闭/启动」这类行为必须真的实现，不能靠相邻机制「顺带」保证**：
  我曾以为计划任务的 `MultipleInstances = IgnoreNew` 就能防止出现两个托盘图标，
  但它只管计划任务触发的启动，**管不住用户手动双击**。验收清单里写了却没实现的项，
  等于埋了一颗雷。现在用命名互斥体 + 自定义消息广播真正实现了单实例。
- **`AutoScroll` 与 `Anchor=Right` 不能同时用**：设置页开了自动滚动后，锚定右边缘的分区每经过一次布局就变宽一次
  （实测从 1361 涨到 2532），右边直接跑出画面。解决办法是只锚左上、由 `Resize` 事件手动算宽度。
  这类「累积漂移」的问题肉眼扫一遍看不出来，必须用断言把「宽度 <= 可视宽度」钉住。
- **界面布局一律用 Dock，不要用「AutoSize 控件 + 绝对坐标 + 固定高度容器」**：
  后者在文字长度会变化的地方必然出问题 —— 「开机自启」详情区就因此压住了下面的按钮（用户实际报的 bug）。
  停靠布局从结构上就不会重叠：该钉住的钉住，剩下的地方自动分配，装不下就滚动。
  凡是长度会变的文字，都不要用绝对坐标。

### 1.2（IP 归属查询）新增的结论

- **「默认开启」这个决定会强制带出「必须能持久关闭」**：开关不落盘的话，
  用户关掉之后重启又会被自动打开 —— 他对隐私的选择被静默回滚。所以加了
  `%LOCALAPPDATA%\WinAppGuard\settings.json`（只存布尔值、原子写入）。
  **默认开启 + 不持久化 = 关不掉**，这两件事必须一起考虑。
- **选择数据源时先量再说，不要凭印象**：原以为「反向 DNS 能拿到域名」，
  实测命中率只有 **25%（40 个地址命中 10 个）**，而且换任何 DNS 解析器
  （阿里 / DNSPod / 114 / Google / Cloudflare）命中集合**完全相同**，
  换解析器一个都不会多 —— 那 75% 是公网上真的没有 PTR 记录。
  RDAP（RIR 权威）覆盖率也只有 **75%**，恰好在本机不通的 ARIN 地址段上全失败。
  最后是 Team Cymru WHOIS 做到 **100% 覆盖**，国家字段与 RDAP 在 9 个重叠 IP 上
  **9/9 一致**。
- **「按主机名连接」隐含一次 DNS 查询**：`TcpClient.ConnectAsync(host, port)` 会先解析
  `whois.cymru.com`。这一步在托管元数据里看不到（我们没有引用 `System.Net.Dns`），
  所以**审计输出和文档都主动写明了**，不能因为审计扫不到就当作不存在。
- **审计口径要跟着能力一起改，否则会变成假报告**：原来的检查是「网络类型必须为 0」。
  加了联网能力之后，如果只是把这条断言删掉，审计就失去了意义。
  正确做法是改成「**全部落在预期清单内**」，并**补一项原生模块的防绕过检查** ——
  因为只看托管类型的话，有人用 `ws2_32` 就能绕过去。**审计的可信度比审计的绿灯更重要。**
- **临时 harness 会写真实的用户数据目录**：本项目的 harness 反射构造真实窗体，
  于是它会真的写 `settings.json` 和日志。正常结束时 `finally` 能清理，
  但**被强杀时会漏** —— 实测就漏了一次，残留的 `settings.json` 里
  `IpOwnershipNoticeShown: true` 会让用户的第一次运行看不到一次性告知。
  验证完后要**检查 `%LOCALAPPDATA%\WinAppGuard\` 是否干净**。
- **给用户用的 `.cmd` 必须纯 ASCII**：`cmd.exe` 用系统 ANSI 代码页解码批处理文件，
  里面的 UTF-8 中文会被解成乱码并**破坏命令解析**（和 PowerShell 5.1 的 BOM 坑同一类）。
  注意 `chcp 65001` 救不了它 —— 那是在**文件已经被解析之后**才执行的。
  现在这个启动器由 `tools\publish-check.ps1` 用 `ASCIIEncoding` 生成，保证不会再犯。

### 1.2.5 新增的结论

- **「启动时长」这种信号会骗人 —— Windows 的「快速启动」**：
  「阻断到下次重启」第一版用「现在 − `Environment.TickCount64`」推算开机时刻来判断是否重启过。
  实测**失效**：用「关机 → 开机」时内核从休眠文件恢复，**开机时长不归零**，
  推出来的开机时刻和上次一模一样，判定成「没重启过」，规则永远不解除。
  修法：再加一个**确定无疑**的信号 —— **本次进程是不是被「登录触发的开机自启」拉起的**；
  两个信号命中任意一个就算过期。
  **教训：判断"系统重启过没有"时，不要依赖单一的时间推导值。**
- **"自动删除"也必须事先同意**：临时阻断到期会自动删规则，而项目的硬性约定是
  「所有会改系统状态的操作必须弹确认框」。自动删除没法再弹（弹了后台程序永远解不开），
  所以把同意放在**创建时**：确认框里写清「规则会在几点几分自动解除」。
  **这类"程序替用户做的后续操作"都要在设计时找地方把同意前置。**
- **一个 `Fill` 列会让它右边那条分隔线拖不动**：`DataGridView` 的 `AutoSizeMode = Fill`
  列宽度是算出来的，不是固定边界，所以**它的右边缘天生不可拖**。
  放在中间就出现「别的线都能拖、唯独那条拖不动」（用户报的 bug）。
  **修法：把 Fill 列放到最后一列。**（顺带：去掉 Fill 列反而更慢 —— 会触发横向滚动条反复开关。）
- **`DataGridViewColumn.Resizable` 会跟着网格的总开关走**：
  为了关掉「自带实时列宽拖动」而设 `AllowUserToResizeColumns = false` 之后，
  `column.Resizable` 会返回 `False` —— 如果命中判断里顺手检查了它，
  就会把**自己实现的拖动也一起关死**（现象：鼠标事件正常、命中测试也对，但拖动永远不开始）。
  **修法：不要检查这个属性。** 这条是靠"用真实鼠标消息驱动"的断言才发现的。
- **`Button.PerformClick()` 在控件不可见时静默地什么都不做**：
  写搜索/清除的断言时，如果当前停在别的标签页，`PerformClick` 会「点了个寂寞」，
  断言就会得到一条**假失败**。**修法：测之前先切回那一页。**
- **临时阻断的到期信息存在规则的说明字段里**（而不是另建文件）：
  好处是规则和时间永远绑在一起、用户在 `wf.msc` 里能直接看到、不新增本机文件
  （也就不会碰到「设置文件只存布尔值」那条约定）。
  代价：说明字段有 255 字符上限，**截断时必须优先保住到期标记**，
  否则长路径会把标记挤掉、规则变永久 —— 用户永远等不到解除，还不知道为什么。
- **定期任务不要在界面线程上做**：过期检查要枚举全部防火墙规则，
  实测本机 735 条要 **46ms**，挂在界面线程上每 30 秒就有一次可见卡顿。
  改后台线程前先验证了「COM 对象从 MTA 线程可用」（实测可以），再动手。

### 1.3（严格模式）新增的结论

- **「改了系统级设置」和「改了规则」是两种性质的东西**：规则改错了，用户点一下就回来了；
  而「默认出站动作」是系统级设置，**不随程序退出而恢复**。所以严格模式的代码规矩完全不同：
  **先落盘意图、再动系统**（先把"我开了"写进 `settings.json`，**然后**才改防火墙），
  并且**三条还原路径**必须齐（正常退出 / 崩溃后启动兜底 / `--cleanup` 与删除全部规则）。
  **教训：任何"改了不会自己恢复"的设置，都必须先能回答"程序没跑完就死了怎么办"。**
- **`--cleanup` / 「删除全部规则」必须先把严格模式关掉**：这两件事会把白名单删光，
  而"默认阻止 + 没有白名单"= 整台机器断网。**顺序也不能反**（先还原、再删规则），
  反的话中间那一瞬间就是断网。
- **护栏要分清方向**：`ProtectedProcesses` 的原始理由是"拦掉它你就没法用界面解除了"——
  这只对「阻止」成立。**放行永远不会把用户锁在外面**，而严格模式**必须**能放行本程序自己
  （否则它自己连 IP 归属都查不了）。所以护栏改成只对阻止生效，并加了一条反向断言。
  （这个坑是 `--strict-mode-test` 实测撞出来的，不是想出来的。）
- **"默认阻止"不等于"白名单"**：Windows 自带的允许规则、别的软件/安装程序建的允许规则
  **仍然会放行**。所以连接列表的「放行」列刻意分成三档
  （`已放行·本工具` / `已放行·其它来源` / `未放行`）—— 把"白名单其实不完整"这件事
  直接摆在用户眼前，而不是让他以为"只有我放行的能上网"。
- **`**` 在 WinForms 里会原样显示**：代码注释里到处用 `**` 表示重点，顺手写进字符串之后，
  用户看到的就是两个星号（Label / 按钮 / 悬停提示都不做 Markdown 渲染）。
  这个坑是**渲染 PNG 时人眼**发现的 —— 于是加了一条自检：扫一遍整个控件树
  （含列头、单元格悬停提示、右键菜单、托盘菜单），发现 `**` 就失败。
  并且**故意把 `**` 塞回去验证过它真的会失败**（否则"通过的断言"可能永远不会失败）。
- **界面文案的正确性只能靠"把真实文字拿出来断言"**：严格模式的说明文字抽成了**纯函数**
  （不读防火墙），这样自检才能直接断言"会话级 / 退出即还原 / 挡不住别人的规则"这些
  **诚实性底线**有没有被改掉。**凡是"我们必须说清楚"的话，都值得抽成可断言的东西。**
- **「会断网的程序清单」算错会真的害人**：清单里多一个会吓人，少一个会真的把用户断网。
  所以它的算法单独用断言钉住了（排除已放行的、排除别人放行的、排除没路径的、同程序去重）。
