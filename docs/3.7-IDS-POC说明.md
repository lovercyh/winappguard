# 3.7 IDS POC 说明（VM）

> 目的：在写产品代码之前，用实测数字回答「用户态 flow IDS 是否值得做、CPU/误报能不能接受」。
> 只在验收 VM 上跑；POC 只读采集 + 本机合成流量，不阻断、不改防火墙。

## 0. 文件

`dist-tools\WinAppGuard.IdsPoc.exe`（单个 exe，36 MB 左右）。

`publish.ps1` 不会自动构建它；本次已经手动同步到 `dist-tools`。

## 1. 合成场景自检

管理员 PowerShell：

```powershell
cd C:\Users\VM\Downloads\默认项目\dist-tools
.\WinAppGuard.IdsPoc.exe --selftest
```

它会依次生成：

- beacon：每 2 秒连接本机回环端口，共 8 次；
- scan：连接 127.0.0.2–127.0.0.16，以及 15 个关闭端口；
- lateral：尝试本机内网网段 6 个地址的 445/3389/5985；
- DNS：查询 30 个随机长域名（`.invalid`）；
- upload：向回环发送 12 MiB。

合计约 30–40 秒。

请记录完整输出，重点：

| 项 | 期望 |
|---|---|
| 时长 | ~30–40 秒 |
| 事件明细 | TCP/UDP 收发、连接事件都有数 |
| flow 峰值 | 小于 20k |
| CPU 平均/峰值 | 目标 <5% |
| 内存峰值 | 目标 <50 MB |
| 告警 | beaconing / scan / lateral / dns / exfil 都应命中 |

如果某条规则**未命中**，把输出贴回来；我先调阈值/解析，不急着写产品。

## 2. 正常使用误报观察

管理员 PowerShell：

```powershell
.\WinAppGuard.IdsPoc.exe --monitor 600
```

运行期间正常使用 10 分钟：

- 浏览网页、看视频；
- 下载一个大文件；
- 打开 Teams / 微信 / 网盘之类的常驻程序；
- 不要运行扫描/beacon 脚本。

记录：

- CPU 平均/峰值、内存峰值；
- flow 峰值、事件总数；
- **是否出现误报**；每条误报的规则、进程、目标、证据。

判定（建议）：

- 0 个高严重度误报；
- 中严重度 ≤2 条/小时；
- CPU <5%，内存 <50 MB。

达不到就缩小规则范围或调整阈值，不硬上。

## 4. 边界

- POC 只看连接元数据和 DNS 域名，不解析载荷、不做 DPI/HTTPS 解密；
- `--selftest` 只连本机/回环/本机内网网段，不对外扫描；
- 如果 ETW 启动失败，通常是没提权；用管理员 PowerShell 重跑；
- POC 与服务可同时运行（会话名不同），但合成流量也会被服务的流量页统计到，属于正常现象。
## 5. 第一轮 POC 结果与调整（2026-10-26）

第一轮 `--selftest` 结果：

- CPU 平均 0.1%、峰值 0.3%（16 核），内存 61 MB，flow 峰值 205，事件 1587/27 秒；
- beaconing / scan / dns / exfil 命中，**lateral 未命中**；
- 出现明显误报：
  - `svchost.exe` 的 mDNS/LLMNR 组播被当成 beaconing；
  - `svchost.exe` / `chrome.exe` 的正常多连接被当成 scan；
  - `svchost.exe` 的大量系统 DNS 被当成 DNS 异常。

已调整 POC：

1. **scan** 只统计 TCP 连接/接受事件；改为「同一主机 ≥15 个端口」或
   「同一非 80/443 端口上 ≥15 台主机」，不再按“端点总数”判。
2. **beaconing** 排除组播/广播/链路本地和 53/5353/5355/1900/3702/137/138；
   最小间隔 5 秒，要求连接 ≥6 次且平均每次数据 <256 KB。
3. **DNS** 按「同一父域」分组，避免系统进程查很多不同域名造成误报。
4. **lateral** 的合成场景改为在本机管理端口临时监听，再连 6 个回环地址，
   验证规则逻辑；生产规则仍限定内网地址。
5. 合成 beacon 改为每 5 秒一次、共 6 次；整个 selftest 约 45–60 秒。
6. 内存目标放宽到 **<80 MB**（POC 包含 .NET 运行时；产品服务按实际基线再定）。

请重新跑 `--selftest` 和 `--monitor 600`，把输出贴回来。
## 6. 最终 POC 结果（2026-10-26）

### 6.1 selftest

- 5 条规则全部命中：beaconing / scan / lateral / dns / exfil；
- 时长约 39–43 秒，事件 1,890，flow 峰值 532，DNS 2,490；
- CPU 平均 0.0%，峰值 0.3–0.4%（16 核）；
- 内存峰值 62 MB。

调试中发现：合成 beacon 的 `Thread.Sleep(5000)` 实际间隔可能是 4.99x 秒，
旧规则要求 `>=5.0` 会漏掉；POC 容差已放宽到 4.0 秒。生产规则会单独定阈值。

### 6.2 monitor 600

- 10 分钟正常使用：**0 条告警**；
- 事件 11,724，flow 峰值 535，DNS 113；
- CPU 平均 0.0%，峰值 0.1%（16 核）；
- 内存峰值 56 MB。

结论：用户态 flow IDS 在性能上完全可行，规则经收紧后 10 分钟无误报。
设计见 `docs/3.7-用户态FlowIDS设计.md`，设计批准后才动产品代码。
## 7. 产品化结果（3.7，2026-10-26）

- POC 的 5 条规则只作为能力验证；产品代码按批准范围只实现 4 条：
  beaconing / scan / lateral / dns，**不做 exfil**。
- 产品规则阈值见 `docs/3.7-用户态FlowIDS设计.md` 第 3 节；
  与 POC 收紧后的规则一致（标准敏感度）。
