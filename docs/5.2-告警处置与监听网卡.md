# 5.2 可行性报告：告警处置免 UAC + 监听网卡可选

> 状态：已实现，待 VM 验收
> 日期：2026-11-05
> 范围：只做“告警确认 / 抑制 / 清空不再弹 UAC”和“监听网卡可选”；不改检测规则，不加自动拦截，不加内核驱动。

## 1. 先核对现状（重要）

“标记已读 / 同类告警不再提醒 / 清空”这三个动作目前实际在 **IDS 页**；反网络攻击页原本只有“清空告警”。

| 页面 | 5.1 的动作 | 5.1 是否弹 UAC | 5.2 的处理 |
|---|---|---|---|
| IDS | 确认 | 是 | 改名“标记已读”，免 UAC |
| IDS | 抑制… | 是 | 改名“同类告警不再提醒”，1h/24h 免 UAC，永久 UAC |
| IDS | 清空… | 是 | 免 UAC |
| 反网络攻击 | 清空告警 | 是 | 免 UAC |
| 反网络攻击 | 无按钮 | — | 新增“标记已读”和状态列 |
| 反网络攻击 | 无此功能 | — | 5.2 不新增“不再提醒” |

5.2 按下面执行：

- IDS 的标记已读 / 同类告警不再提醒 / 清空 + 反网络攻击的清空都免 UAC；
- 反网络攻击页补“标记已读”和已读/未读状态；
- 反网络攻击不新增“不再提醒”，避免把新功能和免 UAC 混在一起。

“标记已读”成本很低（命令和状态都已存在，只差一个按钮）；“同类告警不再提醒”是 IDS 已有功能，本次只改文案和授权方式。

### 1.1 三个动作的区别

| | 标记已读（ack） | 同类告警不再提醒（suppress） | 拦截（block） |
|---|---|---|---|
| 作用对象 | 一条告警的状态 | 未来同类告警 | 真实网络流量 |
| 效果 | 标记为已读，未读数 -1 | 匹配的后续告警不再产生/显示 | 用 WFP 阻断出站连接 |
| 是否影响联网 | 否 | 否 | 是 |
| 是否写 WFP | 否 | 否 | 是 |
| 现有页面 | IDS 和反网络攻击 | 仅 IDS | 反网络攻击 |
| 时长 | 状态保存到告警被清理 | 1 小时 / 24 小时 / 永久 | 1–60 分钟，服务重启自动解除 |
| 5.2 的 UAC 方案 | 免 UAC | 1h/24h 免；永久 UAC | 始终 UAC |
| 是否可撤销 | 界面不提供反向操作 | 可在 IDS 设置里删除 | 可手动释放或到期解除 |
| 误伤 | 无 | 可能漏看同类告警 | 可能断网 |

一句话：

```text
确认 = 这条我看过了
抑制 = 以后同类别再提醒我
拦截 = 真的把流量挡住
```

反网络攻击页的“确认”不是“确认拦截”；为了避免混淆，按钮建议叫“标记已读”或“标记已确认”。

## 2. 现状与约束

### 2.1 为什么现在一定会弹 UAC

不是界面自己想弹，而是服务端的统一规则：

1. 服务管道只允许 **SYSTEM + 受保护模式所有者 SID** 连接，并且要过 ECDSA 挑战签名；
2. `ControlServer.Dispatch` 在最前面统一检查：命令以 `write.` 开头且客户端未提权 → 直接拒绝；
3. 界面 `MainForm.CallService` 在非管理员时走 `ElevatedClient`，由提权助手 `WinAppGuardSvc.exe --elevated-ipc` 拉起 UAC。

```text
GUI（标准用户）
  └─ CallService
       ├─ 已是管理员 → ServiceClient 直接发
       └─ 非管理员   → ElevatedClient → UAC → --elevated-ipc → 服务
```

因此，**只改界面调用方式没有用**，服务端必须明确允许这几类命令以标准用户身份执行。

### 2.2 告警状态现在存在哪里

| 数据 | 位置 | 作用 |
|---|---|---|
| IDS 确认状态 | `%ProgramData%\WinAppGuard\ids\state.json` | 未确认计数、界面状态 |
| IDS 抑制表 | 同上 | 分析器在产生告警前就过滤掉 |
| 反网络攻击确认状态 | `%ProgramData%\WinAppGuard\network-detection\state.json` | 未确认计数 |
| 告警历史 | IDS / network-detection 各自的告警存储 | 清空时删除 |

关键点：**抑制不是纯界面状态**。`IdsHost.TickCore` 会把抑制表交给分析器，匹配的告警根本不会产生。所以抑制不能只存在界面本地，否则“抑制了但告警还在产生”。

### 2.3 可复用的用户级存储

项目已经有 `%LOCALAPPDATA%\WinAppGuard\*.json` 的用户级存储模式（`AppSettings`、`UiState`、`LocalLog`），但本次**不建议**把告警状态搬到用户目录：

- 抑制必须留在服务端才能真正生效；
- 确认状态、未确认计数、托盘通知都以服务端为准，搬走会造成两套状态；
- 服务端已有原子写和保留期清理。

## 3. 方案一：告警处置免 UAC

### 3.1 推荐设计：服务端增加“告警元数据”命令白名单

新增一组命令前缀 `alert.`，明确表示“只改告警元数据，不碰 WFP / 设置 / 拦截”：

| 新命令 | 作用 | 是否免 UAC |
|---|---|---|
| `alert.ids.ack` | 确认一条 IDS 告警 | 是 |
| `alert.ids.suppress` | 新增 / 删除 IDS 抑制 | 是 |
| `alert.ids.clear` | 清空 IDS 告警历史 | 是 |
| `alert.network.ack` | 确认一条反网络攻击告警 | 是 |
| `alert.network.clear` | 清空反网络攻击告警历史 | 是 |

服务端处理：

```text
Dispatch(request)
  ├─ 协议版本检查
  ├─ auth.check / 只读查询
  ├─ alert.*  → 只允许进入告警处理分支（新增的明确 allowlist）
  ├─ write.*  → 仍然必须提权（规则 / 拦截 / 设置 / 严格模式 / 审计…）
  └─ 其它只读命令
```

旧的 `write.ids.ack` 等命令保留为兼容别名，仍然要求提权；新界面只发 `alert.*`。这样：

- 不破坏“`write.` = 系统变更，必须提权”的既有约定；
- 不需要把 `write.` 前缀改成“有时候可以不提权”的模糊规则；
- 老版本界面连新服务仍能工作，新界面连老服务会收到“未知命令”，安装器会同时升级两者。

### 3.2 安全边界

这不是“所有人都能清告警”：

- 管道仍然只有 SYSTEM + 所有者 SID 能连；
- 仍然要过 ECDSA 挑战签名；
- 只是把“所有者用户能不能在不再弹一次 UAC 的情况下处置自己的告警”从“不能”改成“能”。

需要如实写进文档的风险：

- 以所有者身份运行的恶意程序，可以不经管理员同意就确认 / 抑制 / 清空告警；
- 这不是内核级防护，服务本来就是用户态、可被管理员停止；
- 告警历史不是取证级数据，清空只影响告警，不影响 WFP 规则、拦截和设置；
- 服务日志会记录每次 `alert.*` 操作（命令、PID）。

可选加固（不阻塞 5.2）：

- 非管理员只能创建有时限的抑制（1 小时 / 24 小时），永久抑制要求界面已经提权；
- 或者永久抑制仍然弹 UAC，只有 1 小时 / 24 小时免 UAC。这会与“抑制完全免 UAC”略有出入，需要你拍板。

### 3.3 明确不动的命令

以下命令必须继续保持“非提权拒绝”，并加回归测试：

```text
write.network-detection.block
write.network-detection.release
write.network-detection.release-all
write.network-detection.configure
write.ids.configure
write.rules.*
write.strict.*
write.audit.*
```

- 不需要迁移数据：确认状态和抑制表仍在原文件；
- 旧状态文件里的 `ack` 状态继续有效；
- 清空仍然只删告警历史 + 确认状态，不删抑制表（IDS 现状如此）；
- 卸载 / 重装行为不变。

### 3.6 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 标准用户可抑制告警 | 本地恶意程序可降低告警可见性 | 所有者限定 + 服务日志 + 文档说明；可选时限抑制 |
| 误把系统命令加进 allowlist | 可能绕过提权 | allowlist 只写死 5 条 `alert.*`；回归测试覆盖 block/configure 仍被拒 |
| 新界面连旧服务 | 报“未知命令” | 安装器同时升级；错误提示引导 `--repair` |
| 清空误伤 | 告警历史丢失 | 保留确认框；只删告警，不碰规则/拦截/设置 |

## 4. 方案二：监听网卡可选

### 4.1 现状

`SuricataHost.FindCaptureDevice()` 当前逻辑：

1. 枚举所有网卡；
2. 跳过 Loopback、Tunnel、非 Ethernet / Wireless80211 / GigabitEthernet；
3. 优先返回第一块“有网关”的网卡；
4. 启动参数固定为 `-i "\Device\NPF_{GUID}"`。

问题：

- 多网卡时无法选择；
- Hyper-V、VMware、VirtualBox 的虚拟网卡可能排在前面；
- VPN / Tunnel 被直接排除；
- 用户不知道 Suricata 到底在听哪块网卡；
- 换网卡（USB 网卡、Wi-Fi 切换）后没有提示。

### 4.2 推荐设计：单网卡选择（5.2 范围）

**设置模型**（`NetworkDetectionSettings` / `NetworkDetectionSettingsDto`）：

```text
CaptureDeviceId    string   空 = 自动；否则是网卡 GUID（NetworkInterface.Id）
```

**设置界面**（`NetworkDetectionSettingsForm`）：

- 新增“监听网卡”下拉框：
  - `自动（推荐）`
  - 每块网卡：`名称 — 描述（状态）`
- 旁边一个“刷新”按钮，重新枚举；
- 选中非活动网卡时显示提示，但不阻止保存；
- 说明文字：修改后会重启 Suricata，需要一次 UAC。

**服务端解析**：

```text
CaptureDeviceId 为空
  → 走现有 FindCaptureDevice()（保持 5.1 行为）

CaptureDeviceId 有值
  → 按 GUID 找网卡
  → 找到且可用：\Device\NPF_{GUID}
  → 找不到 / 已断开：回退到自动，并记录原因
```

**状态展示**：

- `NetworkDetectionStatusDto` 增加：
  - `CaptureDeviceName`：实际监听的网卡名；
  - `CaptureDeviceFallback`：是否发生过回退；
  - `CaptureDeviceNote`：例如“原选择不可用，已回退到自动”。
- 反网络攻击页状态行显示：`监听：以太网` 或 `监听：自动（已回退）`。

**启动参数**：

```text
-i "\Device\NPF_{GUID}"
```

保持现有参数形式，只把 device 从“自动算出来”改成“按设置解析”。

### 4.3 为什么 5.2 只做单网卡

- 5.2 按单设备使用 `-i`，不承诺多网卡同时抓包；
- 多网卡同时抓包需要 `--pcap` + `suricata.yaml` 的 `pcap.interface` 列表，Windows 下的行为和性能未验证；
- 用户的需求是“能选对网卡”，单网卡已经解决；
- 多网卡留到后续版本，先做 VM 验证再评估。

### 4.4 自动模式要不要改

建议 5.2 **保持现有自动逻辑不变**，只做两件事：

1. 自动模式仍然排除 Tunnel；
2. 手动选择时允许选 Tunnel / 虚拟网卡，并标注“可能抓不到”。

不把“自动”改成按默认路由选：

- VPN 开启时默认路由在隧道上，自动选隧道可能抓不到；
- 现有“物理网卡 + 网关”的策略在大多数单网卡机器上是对的；
- 选错网卡的机器，用户现在可以手动纠正。

可选的小改进（不影响主流程）：自动模式排除描述里明显是 Hyper-V / VMware / VirtualBox 的虚拟网卡，减少选错概率。

### 4.6 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Windows 网卡 GUID 与 Npcap 设备 GUID 不一致 | 选中的网卡抓不到 | 服务端按 GUID 构造 `\Device\NPF_{GUID}`；VM 实测；必要时改用 `pcap_findalldevs` |
| 选中网卡被拔掉 / 禁用 | 检测中断 | 自动回退到自动模式 + 状态提示，不清空用户选择 |
| VPN / 虚拟网卡抓不到 | 用户以为在检测 | 下拉框标注“可能抓不到”；状态显示实际设备 |
| 切换网卡导致短暂漏抓 | 几秒空窗 | 重启前先校验；状态显示“重启中 / 已运行” |
| 设置保存需要 UAC | 与“免 UAC”预期混淆 | 明确区分：告警处置免 UAC，改检测设置仍需 UAC |
| 多网卡机器只监听一块 | 另一块流量看不到 | 5.2 明确单网卡；文档写清楚，多网卡后续评估 |

## 5. 步骤规划

### 5.1 阶段划分

| 阶段 | 内容 | 交付物 | 预计 |
|---|---|---|---|
| P0 | 范围拍板：IDS + 反网络攻击清空；是否补反网络攻击确认；抑制时限策略 | 确认后的范围清单 | 0.5 天 |
| P1 | 服务端 `alert.*` 白名单 + 日志 + 回归测试 | 服务改动、鉴权矩阵测试 | 1–1.5 天 |
| P2 | 界面切换 `CallAlertService`；IDS 三动作 + 反网络攻击清空 | 界面改动、无 UAC 验收 | 0.5–1 天 |
| P3 | 反网络攻击“确认”按钮（可选） | 一个小按钮 + 复用现有命令 | 0.5 天 |
| P4 | 网卡模型 + 纯函数解析器 + 单元测试 | Core 新文件、测试 | 1–1.5 天 |
| P5 | SuricataHost / NetworkDetectionHost 接入 deviceId、回退、状态 | 服务端网卡选择 | 1 天 |
| P6 | 设置界面下拉框 + 状态行 + 本地化 + 布局 | UI 改动、英文文案 | 1 天 |
| P7 | 自检、VM 验收、README/CHANGELOG/截图 | 文档与截图 | 1–2 天 |

合计约 **5.5–8 个工作日**，不含 VM 排队时间。只做主线（不补反网络攻击确认 / 抑制）约 **5–6 天**。

### 5.2 推荐实施顺序

1. **先做 UAC**：改动小、独立、可先验收；不依赖网卡。
2. **再做网卡**：涉及服务重启和设备解析，放在后面单独验证。
3. **最后补反网络攻击“确认”按钮**：如果确认需要，这是最小的一步。

### 5.3 详细步骤

#### 第一步：冻结范围（P0）

- 明确“抑制”只指 IDS 现有抑制，还是也要给反网络攻击加；
- 明确永久抑制是否免 UAC；
- 明确 5.2 只支持单网卡；
- 把结论写回本文档。

#### 第二步：服务端告警命令（P1）

- `ServiceProtocol` 增加 5 条 `alert.*`；
- `ControlServer.Dispatch` 增加精确 allowlist；
- 旧 `write.*` 保持提权；
- 每条 `alert.*` 记录 `pid / command / affected`；
- 自检增加：
  - 标准用户 `alert.*` 成功；
  - 标准用户 `write.network-detection.block` / `configure` / `write.ids.configure` 仍失败；
  - 管理员 `write.*` 仍然成功。

#### 第三步：界面切换（P2）

- `MainForm` 增加 `CallAlertService`；
- IDS 确认 / 抑制 / 清空改用它；
- 反网络攻击清空改用它；
- 失败提示区分“服务未启动”和“权限不足”；
- 手测：标准用户点这三个按钮，不应出现 UAC。

#### 第四步：反网络攻击确认（P3，可选）

- 工具栏加“确认”按钮；
- 选中行且 `Status == "new"` 时可用；
- 走 `alert.network.ack`；
- 刷新后未确认计数减少。

#### 第五步：网卡解析（P4）

- 新增纯函数：

```text
Resolve(selectedId, adapters)
  → DevicePath / Name / Fallback / Reason
```

- 先写测试再接线：
  - 空 ID → 自动；
  - 选中存在且 Up → 精确匹配；
  - 选中不存在 → 回退 + 原因；
  - 选中 Loopback → 回退；
  - 多网卡 → 选择正确。

#### 第六步：服务端接入（P5）

- `NetworkDetectionSettings` 增加 `CaptureDeviceId`；
- `SuricataHost.Start/Reload` 增加参数；

## 7. `suricata -T` 是什么

`-T` 是 Suricata 的 **配置 / 规则自检模式**（test configuration）。

```text
suricata.exe -T -c "<suricata.yaml>" -S "<active.rules>" -l "<日志目录>" \
  --set "classification-file=<classification.config>" \
  --set "reference-config-file=<reference.config>"
```

它做的事：

1. 读取并解析 `suricata.yaml`；
2. 加载 `classification.config`、`reference.config`；
3. 加载 `-S` 指定的规则文件；
4. 初始化检测引擎；
5. **不抓包、不处理流量**，直接退出。

结果判断：

- 退出码 `0`：配置和规则能正常加载；
- 非 `0`：配置或规则有错误；
- 过程中可能打印 `W:` 警告（例如 flowbit 未设置），只要退出码是 `0`，就不算失败。

它能发现：

- YAML 语法 / 路径错误；
- 规则语法错误、未知关键字；
- 重复 SID；
- classification / reference 缺失；
- 规则文件编码或格式问题。

它**不能**发现：

- Npcap / `wpcap.dll` 是否安装；
- 网卡名是否真的能抓包；
- 权限是否足够；
- 运行期崩溃、性能问题；
- 规则是否会误报。

WinAppGuard 5.1 的用法（`SuricataHost.ValidateConfigLocked`）：

1. 按当前分类拼出 `active.rules`；
2. 执行 `suricata -T`，超时 60 秒；
3. 成功 → 启动 / 重启 Suricata，删除旧规则备份；
4. 失败 → 恢复旧的 `active.rules`，保留原进程，显示错误。

所以 `-T` 是“换规则前的闸门”，不是“检测功能自检”。网卡是否选对，仍然要靠运行后的 Suricata 日志和告警来验证。

## 8. 已确认的决定
