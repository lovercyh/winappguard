# 服务化设计（B 方案）：防护服务 + 界面客户端

> 状态：**设计稿（v2，已记录负责人决策），未实现**。
> 目标版本：**3.0**（这是一次架构重构，不再按 2.x 的小版本节奏）。
> 3.0 分三个阶段落地：3.0-a 服务骨架 + 安装/卸载；3.0-b 规则写入迁移；
> 3.0-c 严格模式 / 审计迁移 + 篡改防护 + 无界面运行。
> 本文只描述设计与取舍，不代表已经动工。**任何实现都要先得到负责人确认。**

---

## 1. 先厘清一件事：现在"被杀掉"到底会怎样

很多人以为"界面关掉 = 防火墙失效"，**在本项目里不是这样**：

- 2.0 起规则是 **持久化 WFP 过滤器**，挂在 BFE（内核）里；
- 界面进程退出、被任务管理器结束、甚至根本没启动，规则**照样生效**；
- 严格模式是唯一的例外：它是**动态会话**，进程消失就自动撤销 —— 这是刻意的安全方向。

所以 B 方案的真实收益不在于"规则不丢"，而在于下面三件事：

| 收益 | 说明 |
|---|---|
| **界面/后台常驻** | 服务由 SCM 拉起，界面被结束后可以重新打开；开机即进入工作状态 |
| **权限模型更清楚** | 改规则这种需要管理员的事由服务做；界面不必每次弹 UAC（是否真的去掉 UAC 见 §5.3） |
| **篡改响应** | 服务能发现"我们的子层/规则被外部删除"，按策略提示或修复 |

**B 不解决的问题**（必须写在文档和界面上）：

- 管理员（包括提权后的恶意软件）可以 `sc stop` / 杀服务 / 删规则 —— 不做驱动就挡不住；
- 内核级恶意软件、被篡改的系统组件；
- 用户自己主动关闭保护。

---

## 2. 目标与非目标

### 目标

1. 规则、严格模式会话、审计采集由**一个常驻服务**负责；
2. 界面只做展示与下发指令，**不直接碰 WFP**；
3. 服务崩溃能被 SCM 自动拉起；服务被非法结束能被发现；
4. 没有界面时，规则与审计照常工作；
5. 安装 / 卸载 / 升级 / 恢复都有明确路径，**卸载后不残留规则**。

### 非目标（明确不做）

- ❌ 内核驱动 / WFP callout（要签名证书，与"零费用"冲突）；
- ❌ 防管理员 / 防提权 / 反杀软对抗；
- ❌ 云同步、账号体系、远程管理；
- ❌ 在服务里做"看起来很强"的自我保护（例如 SSDT hook、进程注入）—— 这类技术既不可靠，也会显著提高误报。

## 3. 现状盘点

| 组件 | 现在在哪 | 需要什么权限 |
|---|---|---|
| WFP 规则读写（程序 / IP / 严格模式） | UI 进程（`RuleEngine`） | 管理员 |
| 严格模式动态会话 | UI 进程（`StrictModeManager`） | 管理员 |
| 审计（连接轮询 + WFP 拦截事件 + DNS 快照） | UI 进程（`AuditService`） | 读 DNS / 订阅事件需要管理员 |
| 自启（计划任务） | UI 进程 | 管理员 |
| 设置 / 界面状态 / 分组 | `%LOCALAPPDATA%\WinAppGuard\` | 当前用户 |
| 日志 / 审计文件 | `%LOCALAPPDATA%\WinAppGuard\` | 当前用户 |

服务化之后，**上表前四项要搬进服务**；后两项需要重新划分（见 §6）。

## 4. 方案对比（为什么选 B，而不是 A）

| | A：轻量自保 | B：服务（本文） |
|---|---|---|
| 防非管理员结束进程 | ✅ | ✅ |
| 界面被杀后自动恢复 | ❌ | ✅ |
| 无界面时继续审计 | ❌ | ✅ |
| 开机即工作 | 计划任务（有 UAC 依赖） | ✅ SCM 自启 |
| 等待 UAC 的日常操作 | 每次都要 | 可以省掉（可选） |
| 新增攻击面 | 小 | **中（IPC 是权限边界）** |
| 工程量 | 小 | 大（服务 + IPC + 安装 + 迁移） |

结论：**B 值得做**，但必须先把 IPC 的鉴权、安装卸载和回退路径设计对；否则会做出一个"能用但危险"的服务。

## 5. 架构

### 5.1 进程与职责

```
┌─────────────────────────────┐        named pipe (JSON, 长度前缀)
│ WinAppGuard.exe（UI，每用户）│  ───────────────────────────────┐
│  - 只读展示 / 下发指令       │                                │
│  - 不直接调用 WFP            │                                ▼
└─────────────────────────────┘                 ┌──────────────────────────────┐
                                                │ WinAppGuardSvc（LocalSystem）│
                                                │  - WFP 规则读写               │
                                                │  - 严格模式动态会话           │
                                                │  - 审计采集 + 落盘            │
                                                │  - 篡改巡检                   │
                                                └──────────────────────────────┘
                                                              │
                                                              ▼
                                                    BFE（内核）持久过滤器
```

- **服务**：`WinAppGuardSvc`，显示名「WinAppGuard 防护服务」，启动类型 Automatic（**不延迟**：VM 实测延迟启动经常没被拉起；服务不依赖登录用户）。
- **UI**：沿用现在的 exe；服务不可用时进入"离线模式"（见 §9.3）。
- **共享代码**：`WinAppGuard.Core` 抽成独立程序集，服务和 UI 都引用（避免两套规则逻辑）。

### 5.2 服务生命周期

| 事件 | 行为 |
|---|---|
| 开机 | SCM 拉起服务 → 校验子层 → 启动审计 → 启动篡改巡检 |
| 服务崩溃 | SCM 失败重启策略：5s / 15s / 60s，1 小时后重置计数 |
| 服务被 `sc stop` | 正常停止：关闭审计文件、撤销严格模式会话（安全方向） |
| 服务被强杀 | 严格模式自动撤销（动态会话）；持久规则保留；SCM 重启 |
| 卸载 | 先停服务 → 删除服务 → 询问是否删除规则（默认**保留**并提示如何清理） |

### 5.3 IPC 鉴权（最关键的一节）

**命名管道**：`\\.\pipe\WinAppGuard.Control.v1`

- 消息格式：4 字节小端长度 + UTF-8 JSON；单条上限 64 KB；请求带 `id` 与 `protocolVersion`；
- 管道安全描述符：`LocalSystem` / `Administrators` 完全控制；**`INTERACTIVE` 读写**
  （M1.5：查看/记录免管理员）。写命令由服务端**逐条**校验令牌是否提权，
  而不是靠管道 ACL 一刀切 —— 否则界面永远连不上；
- 服务端收到连接后额外校验：
  1. `GetNamedPipeClientProcessId` → 打开进程 → 取令牌；
  2. 令牌必须已提权（`TokenElevation` = 1）且属于 `Administrators`；
  3. 记录客户端 exe 路径（仅用于日志，**不作为授权依据**）；
  4. **只读命令**（status / ping）允许任何交互用户；`write.*` 命令与 `auth.check` 需要提权。
- 所有指令在服务端**重新校验**（路径、受保护进程、端口范围），不信任 UI 传来的任何东西。

#### UI 还要不要管理员？

| 模式 | 体验 | 风险 | 建议 |
|---|---|---|---|
| **M1：UI 仍以管理员运行**（管道只给管理员） | 每次启动弹 UAC（和现在一样） | 低 | ✅ **2.6 先用这个** |
| M2：UI 普通权限，管道允许交互用户 | 无 UAC | 多用户机器上任何登录用户都能改防火墙；必须额外做会话/用户绑定 | 推迟到 2.8 再评估 |

> 结论：**先做 M1**。服务化的价值（常驻、自动恢复、无界面审计）已经不依赖 M2；
> 把"去掉 UAC"当成后续独立决策，避免为了体验牺牲权限边界。

### 5.4 指令集（v1）

只读：`status`、`listRules`、`listIpRules`、`listGroups`、`getAuditTail`、`getServiceInfo`。
写入：`addProgramRule`、`deleteRule`、`clearBlocklist`、`addIpRule`、`setGroup`、`importRules`、
`enableStrictMode`、`disableStrictMode`、`setAuditOptions`。

- 每条写入指令返回 `{ ok, errorCode, message, affected }`；
- `importRules` 由服务端**整份校验**后再落盘，保持 2.4 的"坏文件整份拒绝"语义；
- 服务端维护自己的已知规则缓存，UI 不再持有权威状态。

## 6. 数据与文件布局

| 内容 | 位置 | 说明 |
|---|---|---|
| 服务配置（审计开关、保留期、严格模式白名单来源等） | `%ProgramData%\WinAppGuard\service.json` | SYSTEM 可写；**不放用户隐私数据** |
| 服务日志 | `%ProgramData%\WinAppGuard\logs\` | 按天分文件，保留 7 天 |
| 审计记录 | `%ProgramData%\WinAppGuard\audit\` | 由服务写；UI 只读 |
| 规则分组 | `%ProgramData%\WinAppGuard\rule-groups.json` | 由服务管（规则名是全局的） |
| UI 界面状态（窗口大小 / 列宽） | `%LOCALAPPDATA%\WinAppGuard\ui-state.json` | 保持每用户 |
| UI 偏好（如"是否显示托盘气泡"） | `%LOCALAPPDATA%\WinAppGuard\settings.json` | 保持每用户 |

> 迁移：2.5 的 `%LOCALAPPDATA%` 数据在首次启动服务时**只读复制**到 ProgramData，
> 原文件保留（回退用），并在日志里写清"复制了哪些文件"。不做自动删除。

## 7. 安全边界与威胁模型

| 威胁 | 现状（2.5） | B 之后 | 说明 |
|---|---|---|---|
| 非管理员结束 UI | 可结束（规则不受影响） | ❌ 不能结束 UI；更不能停服务 | 服务 DACL + SCM |
| 非管理员结束服务 | — | ❌ 默认不能（SCM 需要管理员） | |
| 管理员停服务/删规则 | 可以 | **仍然可以** | 不做驱动就挡不住 |
| 恶意进程调用 IPC 改规则 | — | ❌ 被管道 DACL + 令牌校验挡住 | §5.3 |
| 恶意替换服务 exe | — | ⚠️ 只能在文件 ACL 上做（Program Files 默认管理员可写） | 签名缺失是硬伤 |
| 规则被外部删除 | 不检测 | ✅ 巡检发现 + 托盘提示 | 只提示，不自动重建 |
| IPC 消息伪造 / 重放 | — | 长度前缀 + 单连接单请求；不做跨会话重放保护 | v1 够用 |

**必须写进界面的三句话**：

1. 本程序不防管理员；
2. 停掉服务 = 停掉保护（但已建规则仍在 BFE 里，除非被删）；
3. 规则是否生效与界面是否打开**无关**。

## 8. 安装 / 卸载 / 升级

### 安装

- 安装包（或 `--install-service`）：
  1. 复制到 `C:\Program Files\WinAppGuard\`；
  2. `sc create WinAppGuardSvc binPath= "...\WinAppGuardSvc.exe" start= delayed-auto`；
  3. 配置失败重启：`sc failure WinAppGuardSvc reset= 3600 actions= restart/5000/restart/15000/restart/60000`；
  4. 启动服务并调用 `status` 自检。
- **便携模式**：不安装服务时，UI 保持 2.5 的行为（自己调 WFP），并在设置页明确显示「当前为便携模式，无后台保护」。

### 卸载

1. `sc stop` → `sc delete`；
2. **默认删除本程序创建的全部规则**（负责人 2026-10-19 决定）：
   卸载后 BFE 里仍留着规则会让用户以为"防火墙还在偷偷生效"，这不可接受。
   界面默认勾选「删除全部规则」，并列出将删除的条数；高级用户仍可取消勾选（会明确警告）。
3. 删除 ProgramData 数据（询问）；
4. **绝不**在卸载时静默删除规则 —— 那会让用户以为防火墙坏了。

### 升级

- 服务与 UI 的 `protocolVersion` 必须匹配；不匹配时 UI 只允许只读操作并提示升级；
- 升级时先停服务 → 替换文件 → 启动 → 校验子层与规则完整性。

## 9. 失败与降级

### 9.1 服务起不来

- UI 打开时 `status` 失败 → 顶部横幅：「防护服务未运行」+「尝试启动 / 修复」按钮；
- 修复流程：`sc query` → `sc start` → 仍失败则提示查看 `%ProgramData%\WinAppGuard\logs`。

### 9.2 服务崩溃循环

- SCM 重启三次后仍失败 → 服务自身写 `crash-loop` 标记；
- UI 检测到标记时**不反复弹窗**，只在设置页显示一条红色状态 + 日志入口。

### 9.3 离线模式（重要）

- 服务未安装 / 未运行 → UI 退化为 2.5 模式（自己调 WFP），所有功能可用，但：
  - 没有篡改巡检；
  - 界面关闭后没有审计采集；
  - 每次启动仍需 UAC。
- **离线模式必须显式显示**，不能让用户以为后台在保护。

## 14. 决策记录与修订（2026-10-19，根据负责人反馈）

> 本节优先于前文的默认建议；冲突时以本节为准。

### 14.1 版本与交付形态

- 这次是**架构重构**，版本定为 **3.0**，不拆成 2.x 小版本；
- 交付形态从"单个 exe"变成 **安装包 + 服务 + UI**：
  - `WinAppGuardSetup.exe`（安装 / 升级 / 卸载入口）；
  - `WinAppGuardSvc.exe`（服务）；
  - `WinAppGuard.exe`（界面，可普通权限运行，见 14.2）。
- 安装器**自己写**（C#，不引第三方库）：复制文件、建服务、写失败重启策略、
  写卸载注册项、卸载时停服务并删除规则。构建期工具也不引入第三方安装器，
  避免"零第三方"这条线出现例外。

### 14.2 IPC 权限：完全无 UAC 的代价（**待负责人最终确认**）

负责人倾向"M2：UI 完全不需管理员"。必须明确它的后果：

> 服务如果接受**普通权限进程**的改规则指令，那么**任何以同一用户身份运行的恶意程序**
> 也能发出同样的指令（它不需要"冒充"界面，直接连管道即可）。

也就是说：**M2 = 把"改防火墙需要管理员"降级为"改防火墙只需要当前用户权限"。**

三个可选档位：

| 档位 | 查看/记录 | 改规则 | 权限边界 |
|---|---|---|---|
| **M1**（现状） | 需要管理员 | 需要管理员 | 强，但每次启动都弹 UAC |
| **M1.5（推荐）** | **免管理员** | 改规则时弹一次 UAC | 与现在相同；UAC 从"每次启动"降到"每次改规则" |
| **M2**（负责人倾向） | 免管理员 | 免管理员 | **同用户的任意进程都能改防火墙** |

- M1.5 的实现：UI 普通权限运行；点"保存/删除/导入"时，启动一个**短命的高权限客户端**
  （UAC 一次）去调服务；服务端管道只允许提权令牌。
- M2 的实现：管道允许**控制台会话用户**（`WTSGetActiveConsoleSessionId` + 令牌会话匹配），
  拒绝远程与其他会话；服务端仍然做全部输入校验（但无法区分"用户点的"和"同用户恶意进程发的"）。
- **建议**：M1.5。它在体验上已经解决了"每次开程序都弹 UAC"，同时没有降低安全边界。
  如果坚持 M2，请在文档和 README 里如实写明这条降级。

### 14.3 数据迁移：复制 vs 直接切换（决策分析）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 复制 | 旧数据复制到 `%ProgramData%`，旧文件保留 | 可回退；旧版本仍能看历史 | **两份数据**：旧版本继续写旧位置，服务看不到 → 记录会"分叉"；隐私数据留存两份 |
| B. 直接切换 | 只改指向，旧数据不再使用 | 单一来源，无分叉 | 回退到 2.5 时看不到历史；迁移失败风险 |
| **C. 复制 → 校验 → 删源（推荐）** | 复制并逐文件校验（大小/条数）→ 服务成功启动并确认可读 → **删除源文件** | 迁移失败可回落；成功后无分叉 | 迁移窗口内需要临时双份空间 |

推荐 **C**，并加两条约束：

1. 迁移前把源目录整体改名为 `audit.migrating-<时间>`，失败时改回；
2. `rule-groups.json` / 设置属于"小文件"，直接移动；审计是大头，按 C 处理；
3. 迁移结果写日志（复制了多少个文件、多少条记录、删除了什么），用户可在设置页查看。

> 回退说明：如果用户装回 2.5，新位置的数据它看不到 —— 这一点要在 3.0 发布说明里写清，
> 而不是让用户自己发现"记录不见了"。

### 14.4 规则被外部删除：检测 + 阻止 + 重建

负责人的问题是"是不是其他 app 删除规则" —— 是，常见来源：

- 其他防火墙/安全软件清理"未知过滤器"；
- `netsh wfp del filter` / 第三方 WFP 工具；
- 恶意软件主动清掉安全产品规则；
- 用户手动清理（此时服务会把它当外部删除，需要区分：**服务自己执行的删除不算**）。

WFP 支持给对象设安全描述符，SDK 里确认存在：

- `FwpmSubLayerSetSecurityInfoByKey0`
- `FwpmFilterSetSecurityInfoByKey0`

因此 3.0-c 的做法分三层：

1. **阻止（非管理员）**：给我们的子层和每条过滤器设置 DACL，拒绝非管理员的
   `DELETE` / `WRITE_DAC`。普通程序删不掉；管理员仍可删除（不做驱动就挡不住）。
2. **检测**：服务持有**权威规则副本**（`%ProgramData%\WinAppGuard\rules.json`），
   周期性（以及订阅 WFP 变更通知时）比对"副本 vs BFE 实际"；
   **服务自己执行的操作会先从副本里更新**，不会被误判为篡改。
3. **重建 + 提示**：发现缺失立即按副本重建，并在托盘提示
   「有 N 条规则被外部删除，已恢复」；如果重建失败（例如子层被删、权限被改），
   则持续提示并给出「修复」入口。

> 边界（会写进文档）：**管理员和内核级攻击者仍然能删除/停止**；我们能做到的是
> "非管理员删不掉、删了会被立刻发现并恢复"。

### 14.2.1 为什么"密钥认证"做不到"只有本程序能连"

结论先说：**只要服务接受普通权限进程的连接，同用户的恶意程序就总有办法让服务相信它是界面。**
不是密钥设计得不够好，而是"同一用户"这个前提让所有**在带内**的凭证都失效。

| 做法 | 为什么挡不住同用户恶意程序 |
|---|---|
| 客户端内置固定密钥 | 密钥在 exe 里，恶意程序直接 `strings` / 反编译就能拿到；它自己拼一个请求即可 |
| 安装时随机生成密钥，存文件 | 文件属于该用户（或该用户可读），恶意程序读同一份文件即可 |
| DPAPI 加密密钥 | DPAPI 是**按用户**解密的：同一用户的任何进程都能 `CryptUnprotectData` 解出同一把密钥 |
| 校验客户端 exe 路径 + 哈希 | 能挡住"随便写个程序连管道"，但挡不住：① 用 UI 自动化（`SendInput` / UIAutomation）**操作真正的界面**去点按钮；② 向界面进程注入代码后借它的手发请求 |
| 校验客户端数字签名 | **这是唯一真正有效的**（签名无法伪造）。但本项目零费用、没有代码签名证书 → 不可用 |
| 校验"是不是控制台会话" | 只能挡住远程/其他登录用户，挡不住同会话的恶意程序 |

**根本原因**：认证要证明"请求来自我们的代码"，而"我们的代码"和"恶意代码"在操作系统眼里是**同一个安全主体**（同一个用户、同一个完整性级别）。同一主体内部的区分，只能靠签名（密码学）或提权（安全边界）；**共享密钥做不到**，因为双方都能拿到它。

### 14.2.2 所以实际可选的是这三档

| 档位 | 机制 | 能挡住什么 | 挡不住什么 |
|---|---|---|---|
| **M1.5（推荐）** | 改规则时弹一次 UAC，服务只认提权令牌 | 同用户**未提权**的恶意程序（绝大多数） | 已提权的恶意程序（那时它本来就能直接改 WFP） |
| **M2 + 身份校验** | UI 普通权限；服务校验：控制台会话 + 固定 exe 路径 + 安装时记录的哈希 + 请求 nonce | 随手写的脚本、跨会话/远程调用 | UI 自动化、进程注入、替换 exe（能改 Program Files 就需要管理员） |
| **M2 裸奔** | 只校验会话 | 远程 | 同用户任何程序 |

如果坚持 M2，我会实现 **M2 + 身份校验**（文档 §14.2 已列），并且**在设置页与 README 明确写**：
"界面不需要管理员；代价是同一用户下的其它程序也能修改规则。需要更强边界请使用 M1.5。"

> 换句话说：密钥认证能让攻击"麻烦一点"，但会让用户误以为"已经只有我的程序能连" ——
> 这比没有保护更危险。我们不做这种"看起来安全"的东西。

## 15. 3.0 阶段计划（M1.5）

> 原则：每个阶段**能独立跑、能独立验收**；上一阶段验收不通过就不进入下一阶段。
> 任何 push / 打标签仍然需要负责人单独批准。

### 阶段 0：工程拆分（不改行为）

**目标**：把"能跑的单体 exe"拆成服务与界面能共用的结构，行为零变化。

- 拆出 `WinAppGuard.Core`（类库：WFP、审计、规则、设置、日志）；
- 新增 `WinAppGuard.Contracts`（**纯数据**：IPC 请求/响应 DTO，不含任何逻辑）；
- UI 只引用 Contracts + UI 自身代码；服务引用 Core；
- **验收**：现有 14 套自检全部保持绿色；构建 0 警告；exe 行为与 2.5 完全一致。

### 3.0-a：服务骨架 + 安装/卸载（只读 IPC）

**目标**：服务能装、能起、能被界面看到；**还不接管规则写入**。

| 交付物 | 内容 |
|---|---|
| `WinAppGuardSvc.exe` | LocalSystem；启动时校验子层；命名管道服务端；只读命令 `status / listRules / listIpRules / listGroups` |
| IPC 安全 | 管道 DACL 只给 Administrators + SYSTEM；校验客户端令牌已提权（M1.5 的"读"部分） |
| `WinAppGuardSetup.exe` | 安装到 Program Files；建服务（自动、不延迟）；失败重启策略；卸载注册项；`--repair` |
| 卸载 | 停服务 → 撤销严格模式（若在）→ **默认删除本程序规则**（列出条数；可勾选保留并警告）→ 删服务 → 删文件 |
| UI | 启动时探测服务：显示「服务模式 / 离线模式」；离线模式保持 2.5 行为 |
| 自检 | `--service-install-test`、`--service-ipc-test`、`--service-auth-test`、`--ui-offline-mode-test` |

**验收**：安装后服务运行、UI 显示服务模式；**非管理员客户端被拒绝**；
卸载后无服务、无残留规则；离线模式提示明确。

### 3.0-b：规则写入迁移（M1.5 生效）

**目标**：所有规则操作走服务；UI **不再直接碰 WFP**。

- IPC 写命令：增删规则、清空、分组、导入（服务端整份校验）、IP 规则；
- **M1.5**：UI 平时普通权限；点"保存/删除/导入"时启动一个短命的高权限客户端（UAC 一次），
  服务只认提权令牌；
- 服务持有权威规则副本（`rules.json`），WFP 只是执行层；
- **编译期隔离**：UI 项目不再引用 `Core.Wfp`；新增 `--architecture-test` 断言
  "UI 程序集里不存在 WFP P/Invoke / RuleEngine 引用"；
- **离线模式改为只读**（重要取舍）：服务不可用时不再由 UI 直接改 WFP，规则页只读 +
  「启动/修复服务」入口。否则就得在 UI 里保留一整套 WFP 代码，等于双实现。
- 自检：`--service-rules-test`（增删改查/导入）、`--service-elevation-test`（未提权写入被拒）、
  `--rules-persist-test`（服务重启后规则仍在）。

**验收**：UI 全程以普通权限运行；所有规则操作可用；未提权写入被拒；
服务重启后规则不丢；`--architecture-test` 通过。

### 3.0-c：严格模式 + 审计 + 篡改防护 + 数据迁移

**目标**：把剩下的"常驻价值"搬进服务，并加上可验证的篡改处理。

- **严格模式**：动态会话由服务持有；服务崩溃/被停 = 立即撤销（安全方向）；
  开启/关闭都走 IPC + UAC（避免"未提权就能关保护"）；
- **审计**：采集与落盘都在服务；文件放 `%ProgramData%`；UI 通过 IPC 读取；
  关掉界面后记录继续；
- **篡改防护**：
  - 给子层与每条过滤器设 DACL（`FwpmSubLayerSetSecurityInfoByKey0` /
    `FwpmFilterSetSecurityInfoByKey0`），拒绝非管理员删除；
  - 服务按权威副本定期比对；缺了立即重建 + 托盘提示；
  - 服务自己的删除先更新副本，不误报；
- **数据迁移（方案 C，待确认）**：复制 → 逐项校验 → 服务确认可读 → 删源；
  失败则改名回滚；结果写日志；
- 自检：`--service-strict-test`（崩溃即撤销）、`--service-audit-test`（无 UI 仍记录）、
  `--service-tamper-test`（删一条过滤器 → 自动重建 + 记录事件）、`--service-migrate-test`。

**验收**：上面 4 条全绿；卸载后无残留；文档（README / 安全说明 / 测试用例 / CHANGELOG 3.0）更新；
发布说明里写明"管理员仍可停服务/删规则"。

### 阶段与规模

| 阶段 | 规模 | 主要风险 |
|---|---|---|
| 0 拆分 | 中 | 拆分引入的回归（靠现有 14 套自检兜住） |

## 16. 「离线模式只读」的确切语义（3.0-b 起）

### 16.1 为什么会有这个状态

3.0-b 之后，界面**不再包含任何 WFP 代码**（编译期隔离）。
所以当服务没装 / 没运行 / 起不来时，界面**没有能力**直接读写过滤器。
这是刻意的：如果为了"离线也能改规则"而在界面里保留第二套 WFP 实现，
就会有两套写入路径、两套校验、两套 bug —— 而且界面又得重新要管理员权限。

### 16.2 各页面在离线模式下的行为

| 页面 / 功能 | 服务正常 | 离线（服务停/未装） |
|---|---|---|
| 联网连接（实时连接列表） | 正常 | **正常**（读连接表，不需要服务） |
| 记录（审计） | 正常 | **可读**已有记录；不再产生新记录 |
| 规则列表（黑名单/白名单） | 正常 | **只读**：显示服务最后一次已知的规则快照，顶部标注「服务未运行，以下为上次已知状态」 |
| 改规则（添加/删除/清空/分组/导入） | 弹一次 UAC 后生效 | **按钮禁用**，提示「先启动服务」（提供「启动 / 修复服务」按钮） |
| 导出规则 | 正常 | **可用**（从快照导出，只读操作） |
| 严格模式开关 | 弹一次 UAC 后生效 | **禁用**（会话归服务，服务不在就没有会话） |
| IP 归属 / 签名等只读信息 | 正常 | 正常 |

### 16.3 数据从哪来（快照）

- 服务每次成功写入规则后，会更新 `%ProgramData%\WinAppGuard\rules.json`（权威副本，见 §14.4）；
- 离线时界面读这个副本，因此**仍能看到规则**，但明确标注"不是实时状态"；
- 副本里没有的内容（例如别的程序刚加的规则）离线时看不到 —— 这也是标注"上次已知"的原因。

### 16.4 怎么恢复

1. 界面顶部横幅：「防护服务未运行」→「启动服务」/「修复服务」；
2. `WinAppGuardSetup.exe --repair`（重装服务、保留规则与数据）；
3. 彻底坏掉时：`--recover` 清规则 → 重新安装。

> 提醒：**这不是"便携模式"**。3.0 起要完整功能就必须装服务；
> 便携使用（只读查看 / 导出）仍然可以，但改规则不行。

## 16. 3.0-b 实现备注（2026-10-22）

- **唯一写路径**：界面的规则增删改、分组、导入、到期清理全部经 IPC 交给服务；
  服务端仍调用 `RuleEngine`，因此受保护进程 / 路径校验 / 规则命名与 2.x 完全一致。
- **分层鉴权的落地**：命令名以 `write.` 开头的一律要求客户端已提权（服务端用
  `TokenInspector` 再判一次）；`rules.list` / `rules.filterMap` / `status` / `ping`
  允许交互用户。管道 ACL 仍是 `SYSTEM/Administrators` 完全控制 + `INTERACTIVE` 读写。
- **分组文件**：`%ProgramData%\WinAppGuard\rule-groups.json`。界面首次连上服务时
  把旧用户目录文件导入并删除（失败保留），服务端合并时"现有优先"。
- **离线语义**：服务连不上 = 规则页只读（写按钮禁用 + 页首提示），导出可用；
  连接页的阻止 / 白名单同样禁用。**不做本地回退**，避免两套写路径再次分叉。
- **到期清理**：`write.rules.purgeExpired`（带回 `freshLogonSession`）。
  3.0-b 仍由界面触发（启动 + 定时）；3.0-c 把定时器搬进服务，界面关掉也能清理。
- 规则 DTO 只带界面需要的字段（类型、值、动作、到期、范围、分组、启用）；
  协议仍为 v1（只做加法，不改变已有命令语义）。

## 17. 3.0-c 实现备注（严格模式，2026-10-22）

- 严格模式的动态会话**只存在于服务进程**；界面不再调用 `StrictModeManager`。
  服务停止/崩溃 → 会话随之消失 = 立即撤销；服务停止时还会主动 `Dispose`。
- 服务代界面开启时把**界面 exe** 加进放行清单（`<安装目录>\WinAppGuard.exe`），
  否则严格模式下界面自己查不了 IP 归属。
- 白名单写入（加/删/清空/导入）在服务端完成后自动重建会话；
  界面不再需要"规则变化后刷新严格模式"。
- 到期清理也搬进服务（30 秒定时器），界面关掉也会解除临时阻断。
- 1.x 遗留的"默认阻止出站"兜底由安装器（当前用户身份）或服务（界面传路径）执行。

## 18. 3.0-c 实现备注（离线快照，2026-10-22）

- `%ProgramData%\WinAppGuard\rules.json` 是规则的**权威副本**：
  服务在启动时、以及每次写入（增删改/分组/导入/到期清理）后原子更新它。
- 界面离线（服务停/未装）时读这份副本，显示"上次已知状态"并保持只读；
  快照缺失/损坏/版本不认识时退回空只读状态，不猜、不崩。
- 路径常量统一放在 `Contracts.ServicePaths`，界面与服务共用，避免写两份路径。
- 这份副本也是后续**篡改防护**的比对基准（实际过滤器 vs 应该存在的规则）。

## 19. 3.0-c 实现备注（审计迁移，2026-10-22）

- 采集（连接轮询 + WFP 拦截事件 + DNS 推测）全部在服务进程；界面关闭不影响记录。
- 记录目录 `%ProgramData%\WinAppGuard\audit`；设置 `audit-settings.json`（机器级）。
- 界面只读记录文件；改设置/清空走 `write.audit.*`（必须提权）。
- 清空由服务执行：先停采集（释放文件句柄）→ 删除 → 按原设置恢复。
- 旧记录迁移放在安装/修复（服务停止时）：复制 → SHA-256 校验 → 删源；
  冲突保留双方，绝不覆盖。
- 记录页离线可读；设置控件禁用，状态行明确写「服务未运行，记录已停止」。

## 20. 3.0-c 实现备注（篡改防护，2026-10-22）

- 子层与每条过滤器在**创建时**附带安全描述符：只允许 `SYSTEM` / `Administrators`
  完全控制。不再使用"创建后 SetSecurityInfo"（VM 实测会卡死服务启动）。
- 安全描述符构造失败或 BFE 不接受时退回默认 SD（记日志），保证规则功能可用。
- 服务每 10 秒把 `rules.json`（权威副本）与实际过滤器比对；
  快速删除会被发现并重建，分组一并恢复；到期规则不重建。
- 重建与规则写入共用同一把锁，服务自己的删除会先更新副本，不会误报。
- 界面通过 `ServiceStatus.TamperRebuiltCount` 感知并弹托盘提示；
  管理员仍然可以停服务/删规则 —— 防护目标是普通用户与意外删除，不是对抗管理员。

## 22. 3.0-c 实现备注（界面去管理员，2026-10-22）

- 界面清单 `asInvoker`；读操作（status / rules.list / allowTargets / filterMap）直接 IPC。
