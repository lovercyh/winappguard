# 服务化设计（B 方案）：防护服务 + 界面客户端

> 状态：**设计稿，未实现**。
> 目标版本：2.6（骨架）→ 2.7（规则写入迁移）→ 2.8（严格模式 / 记录迁移 + 无界面运行）。
> 本文只描述设计与取舍，不代表已经动工。**任何实现都要先得到负责人确认。**

---

## 1. 先厘清一件事：现在"被杀掉"到底会怎样

很多人以为"界面关掉 = 防火墙失效"，**在本项目里不是这样**：

- 2.0 起规则是 **持久化 WFP 过滤器**，挂在 BFE（内核）里；
- 界面进程退出、被任务管理器结束、甚至根本没启动，规则**照样生效**；
- 严格模式是唯一的例外：它是**动态会话**，进程消失就自动撤销 —— 这是刻意的安全方向。

所以 B 方案的真实收益不在于"规则不丢"，而在于下面三件事：

| 收益 | 说明 |
|---|---|
| **界面/后台常驻** | 服务由 SCM 拉起，界面被结束后可以重新打开；开机即进入工作状态 |
| **权限模型更清楚** | 改规则这种需要管理员的事由服务做；界面不必每次弹 UAC（是否真的去掉 UAC 见 §5.3） |
| **篡改响应** | 服务能发现"我们的子层/规则被外部删除"，按策略提示或修复 |

**B 不解决的问题**（必须写在文档和界面上）：

- 管理员（包括提权后的恶意软件）可以 `sc stop` / 杀服务 / 删规则 —— 不做驱动就挡不住；
- 内核级恶意软件、被篡改的系统组件；
- 用户自己主动关闭保护。

---

## 2. 目标与非目标

### 目标

1. 规则、严格模式会话、审计采集由**一个常驻服务**负责；
2. 界面只做展示与下发指令，**不直接碰 WFP**；
3. 服务崩溃能被 SCM 自动拉起；服务被非法结束能被发现；
4. 没有界面时，规则与审计照常工作；
5. 安装 / 卸载 / 升级 / 恢复都有明确路径，**卸载后不残留规则**。

### 非目标（明确不做）

- ❌ 内核驱动 / WFP callout（要签名证书，与"零费用"冲突）；
- ❌ 防管理员 / 防提权 / 反杀软对抗；
- ❌ 云同步、账号体系、远程管理；
- ❌ 在服务里做"看起来很强"的自我保护（例如 SSDT hook、进程注入）—— 这类技术既不可靠，也会显著提高误报。

## 3. 现状盘点

| 组件 | 现在在哪 | 需要什么权限 |
|---|---|---|
| WFP 规则读写（程序 / IP / 严格模式） | UI 进程（`RuleEngine`） | 管理员 |
| 严格模式动态会话 | UI 进程（`StrictModeManager`） | 管理员 |
| 审计（连接轮询 + WFP 拦截事件 + DNS 快照） | UI 进程（`AuditService`） | 读 DNS / 订阅事件需要管理员 |
| 自启（计划任务） | UI 进程 | 管理员 |
| 设置 / 界面状态 / 分组 | `%LOCALAPPDATA%\WinAppGuard\` | 当前用户 |
| 日志 / 审计文件 | `%LOCALAPPDATA%\WinAppGuard\` | 当前用户 |

服务化之后，**上表前四项要搬进服务**；后两项需要重新划分（见 §6）。

## 4. 方案对比（为什么选 B，而不是 A）

| | A：轻量自保 | B：服务（本文） |
|---|---|---|
| 防非管理员结束进程 | ✅ | ✅ |
| 界面被杀后自动恢复 | ❌ | ✅ |
| 无界面时继续审计 | ❌ | ✅ |
| 开机即工作 | 计划任务（有 UAC 依赖） | ✅ SCM 自启 |
| 等待 UAC 的日常操作 | 每次都要 | 可以省掉（可选） |
| 新增攻击面 | 小 | **中（IPC 是权限边界）** |
| 工程量 | 小 | 大（服务 + IPC + 安装 + 迁移） |

结论：**B 值得做**，但必须先把 IPC 的鉴权、安装卸载和回退路径设计对；否则会做出一个"能用但危险"的服务。

## 5. 架构

### 5.1 进程与职责

```
┌─────────────────────────────┐        named pipe (JSON, 长度前缀)
│ WinAppGuard.exe（UI，每用户）│  ───────────────────────────────┐
│  - 只读展示 / 下发指令       │                                │
│  - 不直接调用 WFP            │                                ▼
└─────────────────────────────┘                 ┌──────────────────────────────┐
                                                │ WinAppGuardSvc（LocalSystem）│
                                                │  - WFP 规则读写               │
                                                │  - 严格模式动态会话           │
                                                │  - 审计采集 + 落盘            │
                                                │  - 篡改巡检                   │
                                                └──────────────────────────────┘
                                                              │
                                                              ▼
                                                    BFE（内核）持久过滤器
```

- **服务**：`WinAppGuardSvc`，显示名「WinAppGuard 防护服务」，启动类型 Automatic（延迟启动）。
- **UI**：沿用现在的 exe；服务不可用时进入"离线模式"（见 §9.3）。
- **共享代码**：`WinAppGuard.Core` 抽成独立程序集，服务和 UI 都引用（避免两套规则逻辑）。

### 5.2 服务生命周期

| 事件 | 行为 |
|---|---|
| 开机 | SCM 拉起服务 → 校验子层 → 启动审计 → 启动篡改巡检 |
| 服务崩溃 | SCM 失败重启策略：5s / 15s / 60s，1 小时后重置计数 |
| 服务被 `sc stop` | 正常停止：关闭审计文件、撤销严格模式会话（安全方向） |
| 服务被强杀 | 严格模式自动撤销（动态会话）；持久规则保留；SCM 重启 |
| 卸载 | 先停服务 → 删除服务 → 询问是否删除规则（默认**保留**并提示如何清理） |

### 5.3 IPC 鉴权（最关键的一节）

**命名管道**：`\\.\pipe\WinAppGuard.Control.v1`

- 消息格式：4 字节小端长度 + UTF-8 JSON；单条上限 64 KB；请求带 `id` 与 `protocolVersion`；
- 管道安全描述符：**只允许 `Administrators` 与 `LocalSystem`**；
- 服务端收到连接后额外校验：
  1. `GetNamedPipeClientProcessId` → 打开进程 → 取令牌；
  2. 令牌必须已提权（`TokenElevation` = 1）且属于 `Administrators`；
  3. 记录客户端 exe 路径（仅用于日志，**不作为授权依据**）；
- 所有指令在服务端**重新校验**（路径、受保护进程、端口范围），不信任 UI 传来的任何东西。

#### UI 还要不要管理员？

| 模式 | 体验 | 风险 | 建议 |
|---|---|---|---|
| **M1：UI 仍以管理员运行**（管道只给管理员） | 每次启动弹 UAC（和现在一样） | 低 | ✅ **2.6 先用这个** |
| M2：UI 普通权限，管道允许交互用户 | 无 UAC | 多用户机器上任何登录用户都能改防火墙；必须额外做会话/用户绑定 | 推迟到 2.8 再评估 |

> 结论：**先做 M1**。服务化的价值（常驻、自动恢复、无界面审计）已经不依赖 M2；
> 把"去掉 UAC"当成后续独立决策，避免为了体验牺牲权限边界。

### 5.4 指令集（v1）

只读：`status`、`listRules`、`listIpRules`、`listGroups`、`getAuditTail`、`getServiceInfo`。
写入：`addProgramRule`、`deleteRule`、`clearBlocklist`、`addIpRule`、`setGroup`、`importRules`、
`enableStrictMode`、`disableStrictMode`、`setAuditOptions`。

- 每条写入指令返回 `{ ok, errorCode, message, affected }`；
- `importRules` 由服务端**整份校验**后再落盘，保持 2.4 的"坏文件整份拒绝"语义；
- 服务端维护自己的已知规则缓存，UI 不再持有权威状态。

## 6. 数据与文件布局

| 内容 | 位置 | 说明 |
|---|---|---|
| 服务配置（审计开关、保留期、严格模式白名单来源等） | `%ProgramData%\WinAppGuard\service.json` | SYSTEM 可写；**不放用户隐私数据** |
| 服务日志 | `%ProgramData%\WinAppGuard\logs\` | 按天分文件，保留 7 天 |
| 审计记录 | `%ProgramData%\WinAppGuard\audit\` | 由服务写；UI 只读 |
| 规则分组 | `%ProgramData%\WinAppGuard\rule-groups.json` | 由服务管（规则名是全局的） |
| UI 界面状态（窗口大小 / 列宽） | `%LOCALAPPDATA%\WinAppGuard\ui-state.json` | 保持每用户 |
| UI 偏好（如"是否显示托盘气泡"） | `%LOCALAPPDATA%\WinAppGuard\settings.json` | 保持每用户 |

> 迁移：2.5 的 `%LOCALAPPDATA%` 数据在首次启动服务时**只读复制**到 ProgramData，
> 原文件保留（回退用），并在日志里写清"复制了哪些文件"。不做自动删除。

## 7. 安全边界与威胁模型

| 威胁 | 现状（2.5） | B 之后 | 说明 |
|---|---|---|---|
| 非管理员结束 UI | 可结束（规则不受影响） | ❌ 不能结束 UI；更不能停服务 | 服务 DACL + SCM |
| 非管理员结束服务 | — | ❌ 默认不能（SCM 需要管理员） | |
| 管理员停服务/删规则 | 可以 | **仍然可以** | 不做驱动就挡不住 |
| 恶意进程调用 IPC 改规则 | — | ❌ 被管道 DACL + 令牌校验挡住 | §5.3 |
| 恶意替换服务 exe | — | ⚠️ 只能在文件 ACL 上做（Program Files 默认管理员可写） | 签名缺失是硬伤 |
| 规则被外部删除 | 不检测 | ✅ 巡检发现 + 托盘提示 | 只提示，不自动重建 |
| IPC 消息伪造 / 重放 | — | 长度前缀 + 单连接单请求；不做跨会话重放保护 | v1 够用 |

**必须写进界面的三句话**：

1. 本程序不防管理员；
2. 停掉服务 = 停掉保护（但已建规则仍在 BFE 里，除非被删）；
3. 规则是否生效与界面是否打开**无关**。

## 8. 安装 / 卸载 / 升级

### 安装

- 安装包（或 `--install-service`）：
  1. 复制到 `C:\Program Files\WinAppGuard\`；
  2. `sc create WinAppGuardSvc binPath= "...\WinAppGuardSvc.exe" start= delayed-auto`；
  3. 配置失败重启：`sc failure WinAppGuardSvc reset= 3600 actions= restart/5000/restart/15000/restart/60000`；
  4. 启动服务并调用 `status` 自检。
- **便携模式**：不安装服务时，UI 保持 2.5 的行为（自己调 WFP），并在设置页明确显示「当前为便携模式，无后台保护」。

### 卸载

1. `sc stop` → `sc delete`；
2. 询问：保留规则 / 删除全部规则（默认保留）；
3. 删除 ProgramData 数据（询问）；
4. **绝不**在卸载时静默删除规则 —— 那会让用户以为防火墙坏了。

### 升级

- 服务与 UI 的 `protocolVersion` 必须匹配；不匹配时 UI 只允许只读操作并提示升级；
- 升级时先停服务 → 替换文件 → 启动 → 校验子层与规则完整性。

## 9. 失败与降级

### 9.1 服务起不来

- UI 打开时 `status` 失败 → 顶部横幅：「防护服务未运行」+「尝试启动 / 修复」按钮；
- 修复流程：`sc query` → `sc start` → 仍失败则提示查看 `%ProgramData%\WinAppGuard\logs`。

### 9.2 服务崩溃循环

- SCM 重启三次后仍失败 → 服务自身写 `crash-loop` 标记；
- UI 检测到标记时**不反复弹窗**，只在设置页显示一条红色状态 + 日志入口。

### 9.3 离线模式（重要）

- 服务未安装 / 未运行 → UI 退化为 2.5 模式（自己调 WFP），所有功能可用，但：
  - 没有篡改巡检；
  - 界面关闭后没有审计采集；
  - 每次启动仍需 UAC。
- **离线模式必须显式显示**，不能让用户以为后台在保护。

## 10. 测试计划（全部进自检）

| 自检 | 内容 | 环境 |
|---|---|---|
| `--service-install-test` | 安装 → 启动 → status → 卸载 → 无残留 | VM 管理员 |
| `--service-ipc-test` | 指令往返 / 版本不匹配 / 超长消息 / 坏 JSON | VM 管理员 |
| `--service-auth-test` | **非管理员客户端连接被拒绝**（用标准用户令牌） | VM（两个账号） |
| `--service-crash-test` | 强杀服务 → SCM 重启 → 规则仍在 → 严格模式已撤销 | VM 管理员 |
| `--service-audit-test` | 服务运行、UI 关闭 → 审计文件继续产生 | VM 管理员 |
| `--service-recover-test` | 服务坏掉时 `--recover` 仍能清规则 | VM 管理员 |
| `--ui-offline-mode-test` | 服务不可用时 UI 显示"离线模式"且功能可用 | 本机 / VM |

> 与现有约定的衔接：会改系统状态的测试继续**只在 VM 里跑**；
> 离线自检（解析、鉴权判定、消息编解码）仍可在开发机跑。

## 13. 本设计的"不做假"承诺

- 不把"服务在运行"包装成"已经防住攻击"；
- 不在服务里做任何无法被自检验证的自我保护；
- 如果某项（例如无 UAC）无法安全实现，就明确写"不做"，而不是留一个看似可用的开关。
