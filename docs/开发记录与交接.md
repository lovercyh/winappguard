## 0. 一句话状态

WinAppGuard 是一个 Windows 图形界面的防火墙规则管理工具，已开源发布到 **v1.2.0**，
仓库 <https://github.com/lovercyh/winappguard>，CI 绿、文档齐、无已知缺陷。

**线上最新是 v1.4.0**（2026-10-17 发布）：在 1.3.0 的基础上新增了**命令行模式**
（`--block` / `--list-blocked` / `--unblock-all`），供脚本化与批量部署使用。
它同时也是本工具第一次提供"无人值守"的操作方式，因此带来了一次**安全约定上的例外**
（CLI 不弹确认框，用管理员权限 / `--yes` / 退出码来补偿，见 §4.2 第 12 条）。

> 版本号的变化过程：这批改动先后被标成 1.2.1 → 1.2.5 → **1.3.0**。
> 最后定在 1.3.0 是因为严格模式动了程序的能力边界，够得上一次小版本。

## 1. 项目是什么

**它本身不处理任何流量**，真正生效的是 Windows 筛选平台（WFP）里的过滤器。它只负责：

- 列出当前正在联网的 TCP 连接（从「谁在联网」入手，而不是翻程序列表）
- 按程序路径创建 / 删除出站过滤器（落在本工具专属的 WFP 子层里）
- 检查程序的**数字签名**（内嵌签名 + 目录签名两条路径都查）
- 可选的系统托盘 + 开机自启（任务计划程序）

**关键差异化**：它提供**可验证的信任** —— `--audit` 模式直接读编译产物的元数据，
证明零第三方库、**联网能力被限定在一处并如实列出**、只有 17 个原生调用。
同类工具里少见。

> ⚠️ **1.2 起「程序自身零网络代码」这句话不再成立**：新增了 IP 归属查询
> （唯一的联网出口是 `Core/IpOwnershipLookup.cs`）。审计口径已改成「**联网边界受控**」——
> 不再要求网络类型为零，而是要求全部落在预期清单内、且不允许用 P/Invoke 绕开。
> 详见第 4 节的约定和第 7 节 1.2 的踩坑记录。

## 4. ★ 必须遵守的约定（破了会出问题）

### 4.1 语言与风格

- **代码注释、提交信息、Issue、PR 全部用中文。** 对外 README 是英文，但代码注释是中文，
  混进英文注释会让整个文件读起来割裂。
- **构建必须 0 警告 0 错误。** 警告在这个项目里当缺陷处理，CI 用 `-warnaserror` 卡住。
- 不引入第三方库。能用 BCL 解决就用 BCL。
- 注释要解释**为什么**，不是**做什么**。代码本身说明做了什么。

### 4.2 安全红线（安全边界，改动需要特别说明理由）

1. **只创建和删除 `AppGuard_` 前缀的规则** —— `FirewallManager.DeleteRule` 里有硬性校验，
   不要把校验挪到界面层。
2. **不修改全局防火墙策略 —— 唯一例外是严格模式**（1.3 起的）：
   `FirewallManager.SetOutboundDefaultAllowed` 是**全项目唯一**会写全局策略的方法，
   只被 `Core/StrictModeManager.cs` 调用。动它之前必须同时满足：
   **先落盘意图再动系统**、**三条还原路径齐备**（正常退出 / 启动兜底 / `--cleanup` 与删除全部规则）、
   **原值不是「三套全允许」就拒绝开启**（绝不覆盖别人的策略）。
   `FirewallEnabled` 与 `DefaultInboundAction` **仍然只读**。
3. **关键进程保护做在防火墙底层**（`FirewallManager.ValidateProgramPath`），不能只做界面置灰。
   ⚠️ **它只限制「阻止」，不限制「允许」**（`forBlocking` 参数）：放行不会把用户锁在外面，
   而严格模式必须能放行本程序自己。
4. **不用注册表做持久化** —— 开机自启只用任务计划程序，设置只写 `%LOCALAPPDATA%` 下的文件。
5. **日志只写本机、不上传；设置文件也只写本机、只存布尔值**（不存 IP / 路径 / 时间戳）。
6. **联网只能从 `Core/IpOwnershipLookup.cs` 这一个出口走**，只连
   `AppConstants.OwnershipLookupHost:OwnershipLookupPort` 这一个固定地址。
   改这两个常量等于改变「程序会对谁说话」——**必须同步改文档并跑 `--audit`**。
7. **私有 / 回环 / 链路本地 / 未指定地址必须在发送前就被过滤掉**
   （`IpOwnershipLookup.IsQueryable`）。不能依赖服务端返回 NA ——
   设计目标是这些地址**根本不出本机**。
8. **归属查询失败绝不能影响主功能**：一律降级成 `Failed` 状态，不向上抛异常；
   界面线程上也绝不做网络 IO。
9. **所有会改系统状态的操作必须走 `ConfirmForm` 弹确认框。**
10. **「程序自己发起的后续操作」也要事先同意**：例如临时阻断到期会**自动删规则**——
    自动删除没法再弹确认框（弹了后台程序就永远解不开），所以同意必须**前置到创建时**
    （`ConfirmForm` 的「阻断时长」会把「几点几分自动解除」写清楚）。
    以后再加类似机制时，别用它当"事后不需要同意"的借口。
    严格模式的还原同理（程序退出 / 崩溃兜底时没法再问），所以同意放在**开启时那两次确认**里。
11. **界面字符串里不要写 Markdown 强调符（`**`）**：WinForms 不做 Markdown 渲染，
    用户看到的就是两个星号。代码注释里可以随便用，**字符串里不行** ——
    自检会扫一遍整个控件树（含列头、单元格悬停提示、右键菜单、托盘菜单）来守着这条。
12. **命令行模式不弹确认框 —— 这是唯一一处对"危险操作必须确认"的例外**（1.4 起）。
    无人值守时弹框等于废掉自动化，所以约定改成「**命令行参数本身就是明确指令**」。
    动 CLI 代码时必须保住三道补偿：**需要管理员权限**、**`--unblock-all` 必须 `--yes`**、
    **逐条打印 + 明确退出码**。**图形界面里的确认框一条都不能放宽。**

### 4.3 ★ 界面布局的三条铁律（每一条都是踩过坑换来的）

1. **用 Dock 布局，不要用「`AutoSize` 控件 + 绝对坐标 + 固定高度容器」。**
   后者在文字长度会变化的地方**必然**出问题 —— 「开机自启」详情区因此压住过下面的按钮
   （用户实际报的 bug）。
2. **`AutoScroll` 和 `Anchor = Right` 不能同时用。**
   容器每布局一次控件就变宽一次（实测从 1361 涨到 2532），右边直接跑出画面。
   解法：只锚左上，宽度由 `Resize` 事件手动算。
3. **`DataGridView` 的 `CurrentRow` ≠ 用户选中。**
   它会在数据绑定后、以及**标签页重新显示时**自动把第一行设为当前行，
   把 `CurrentCell` 设成 null 也挡不住切标签页。
   解法：用独立的 `_connectionSelectionConfirmed` / `_ruleSelectionConfirmed` 标志，
   操作按钮只认这个标志。

另外：**WinForms 的 Label 不解析 Markdown**，别在 Text 里写 `**粗体**`，会原样显示。

### 4.4 ★ 数据与线程（这三条各自对应一次崩溃或诡异行为）

1. **绑定给 `BindingSource` 的 `List<T>` 只创建一次（`readonly`），之后用 `Clear` + `AddRange`
   原地更新，绝不能重新赋值。** 否则 BindingSource 还指着旧列表，表格永远是空的。
2. **顺序必须是：先抓选中项 → 再替换数据 → 最后重绑。**
   反过来的话，列表一旦变短，表格里旧行的索引就越界，
   `CurrentRow.DataBoundItem` 会抛 `IndexOutOfRangeException` **把程序搞崩**。
3. **后台线程不能直接遍历 UI 线程会改的 List。** 先在 UI 线程做快照（`.ToArray()`），
   后台只处理快照里的对象引用。

## 5. ★ 环境相关的坑（本地能跑、CI 跑不了，或反过来）

### 5.1 网络：HTTPS 到 github.com 不通，必须走 SSH over 443

这台机器的网络环境会**按域名干扰 github.com 的 TLS 握手**：

```
Test-NetConnection github.com -Port 443  → 通（TCP 层）
curl https://github.com                  → 退出码 35（SSL 握手失败），0.16 秒被断
git push（HTTPS）                        → Recv failure: Connection was reset
```

**解**：`%USERPROFILE%\.ssh\config` 里已配好把 `github.com` 映射到 `ssh.github.com:443`：

```
Host github.com
    HostName ssh.github.com
    Port 443
    User git
```

remote 也已经是 SSH 形式：`git@github.com:lovercyh/winappguard.git`。
**不要改回 HTTPS**，改了就用不了。

如果哪天 SSH 也不通，还有备选：让代理工具（本机装的是 `Steam++.Accelerator`，
PAC 在 `127.0.0.1:26561`）跑起来，然后给 git 配 `http.proxy`。

### 5.2 PowerShell 5.1 / cmd 的编码坑（踩过三次）

- **含中文的 `.ps1` 必须存成带 UTF-8 BOM 的格式。**
  Windows PowerShell 5.1 会按 ANSI 解析无 BOM 的 UTF-8 脚本，中文注释会解码错乱，
  **进而导致语法错误、脚本直接跑不起来**。项目里的两个 `.ps1` 都带了 BOM，
  `.gitattributes` 里也把 `*.ps1` 标成了 `-text` 防止被搞坏。
- **不要用 `Get-Content` / `Set-Content` 批量改含中文的 `.cs` 文件** ——
  同样会读乱再写回去，把文件毁掉。要用：
  ```powershell
  [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
  [System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding($false)))
  ```
- **给用户用的 `.cmd` 必须纯 ASCII。**（1.2 踩到，见 §7 第 19 条）
  `cmd.exe` 用系统 ANSI 代码页解码批处理文件，UTF-8 中文会被解成乱码
  **并破坏命令解析**。`chcp 65001` 救不了它 —— 那是在文件已经被逐行解析之后才执行的。
  现在 `dist-tools\运行自检.cmd` 由 `tools\publish-check.ps1` 用 `ASCIIEncoding` 生成。

### 5.3 MSBuild / 发布相关的坑

1. **`dotnet restore`（不带 `-c`）+ `dotnet build -c Release --no-restore` → `NETSDK1047`。**
   因为 `RuntimeIdentifier` 写在 `Condition="'$(Configuration)' == 'Release'"` 里，
   不带 `-c` 的 restore 是按 Debug 还原的，没有 win-x64 的资产。
   **Release 那步不要加 `--no-restore`。**
2. **单独 `dotnet build tools/SelfCheck -c Release`（不带 RID）→ `NETSDK1151`。**
   「自包含的可执行文件不能被非自包含的可执行文件引用」。
   自检工具的 csproj 里在 Release 段声明了和产品一致的 RID / SelfContained 配置。
3. **`app.manifest` 的 XML 注释里不能出现连续两个减号。**
   曾经在注释里写了 `--audit`，清单变成非法 XML，**程序启动报「并行配置不正确」——
   而 MSBuild 不校验这个，构建照样成功**，只在运行时炸。
4. **不要开 `PublishTrimmed`。** WinForms 大量依赖反射和 COM，裁剪后会在运行时才报错。

### 5.4 其他

- **自检工具的清单刻意是 `asInvoker` 而不是 `requireAdministrator`。**
  因为 CI（GitHub runner）无法弹 UAC，如果强制提权，连只读的 `--audit` 都起不来。
  需要管理员权限的模式由程序自己检测并提权（见 `tools/SelfCheck/Program.cs`）。
- **.NET SDK 会把 git 提交号附在版本后面**（形如 `1.1.0+5a7219c22e75…`）。
  这是标准行为且有用（用户报 bug 能定位到提交），状态栏里截成短号显示。
- **单文件 exe 的元数据读不到我们的代码**（它是宿主程序，我们的程序集被打包在里面）。
  所以 `--audit` 审计的是 **`WinAppGuard.dll`**，不是 exe。

## 6. 开发历程

项目是分 9 个阶段做出来的，每个阶段只达成一个目标、每阶段结束都停下来让项目负责人验证：

| 阶段 | 目标 | 结果 |
|---|---|---|
| 0 | 项目骨架 / 管理员权限 / 单文件发布打通 | ✅ |
| 1 | TCP 连接枚举与列表（含三层默认过滤） | ✅ |
| 2 | 防火墙规则底层能力 + 17 项安全护栏 | ✅ |
| 3 | 阻止 / 允许单个程序 | ✅ |
| 4 | 规则管理页 —— **修掉「阻止后无法恢复」的设计缺陷** | ✅ |

## 7. ★ 踩坑清单（最有价值的部分）

### 用户在实际测试中发现的问题（4 个）

1. **阻止程序后无法恢复联网** —— 最初把「允许联网」的入口放在**实时连接列表**里，
   但被阻止的程序连不上网、也就不会出现在列表里。**拦截越成功越无法恢复。**
   修法：把恢复入口挂在**持久化的防火墙规则**上（新增「规则」页）。
   **这是最严重的一个，属于设计缺陷，不是代码 bug。**

2. **重复启动出现两个托盘图标** —— 原先只依赖计划任务的 `Instances=IgnoreNew` 策略，
   它只管计划任务触发的启动，**管不住用户手动双击**。
   验收清单里写了「不会出现两个图标」却从没实现过。
   修法：命名互斥体 + 广播窗口消息，第二个实例把已有窗口叫到前台后退出。

3. **「任务详情」文字变长压住了下面的按钮** —— `AutoSize` 标签 + 绝对坐标 + 固定高度容器。
   修法：改 Dock 布局，详情区开 `AutoScroll`。**见 4.3 铁律 1。**

4. **开机自启开启后按钮被挡住**（同上一条的另一个表现）。

### 自测中发现的（6 个）

5. **表格永远是空的** —— `BindingSource.DataSource` 绑的是初始那个空 List，
   而扫描完 `_connections = connections` 换掉了引用。**见 4.4 铁律 1。**
6. **连接数变少时程序崩溃**（`IndexOutOfRangeException`）—— 先替换数据再读表格当前行。
   **见 4.4 铁律 2。**
7. **切一次标签页，安全保护就失效** —— `DataGridView` 会自己选第一行。
   **见 4.3 铁律 3。**
8. **托盘图标糊** —— `new Icon(stream, size)` 只挑「不大于目标尺寸的最大一张」，
   125% DPI 下退到 16×16 再被系统拉伸。修法：把 16/20/24/28/32 全烘焙进 ico。
9. **`AutoScroll` 与 `Anchor=Right` 打架**，控件越排越宽。**见 4.3 铁律 2。**
10. **`notepad.exe` 被误判成「未签名」** —— `WinVerifyTrust` 只查内嵌签名，
    而大量 Windows 系统文件只有目录签名。**见下一条。**

### 开源/CI 阶段发现的（4 个）

11. **CI 的 `NETSDK1047`** —— 见 5.3 第 1 条。
12. **Node 20 弃用警告** —— action 版本太老（checkout v4 → v7 等）。
13. **发布说明被 PowerShell 搞乱** —— 双引号 here-string 会把 markdown 的代码围栏
    （反引号）当转义符。修法：改用**单引号** here-string + 占位符 Replace。
14. **`app.manifest` 的 XML 注释里有 `--`** —— 见 5.3 第 3 条。

### v1.1.0 签名功能本身的坑

15. **只查内嵌签名会漏掉一半** —— Windows 有两套签名机制：

    | 机制 | 位置 | 谁在用 |
    |---|---|---|
    | 内嵌签名 | exe 自己的 PE 证书表 | 第三方软件基本都用这种 |
    | 目录签名 | `C:\Windows\System32\CatRoot\` 的 `.cat` | **大量 Windows 系统文件只有这种** |

    `notepad.exe` / `cmd.exe` / `winver.exe` 都属于第二类。
    验证方法：读 PE 头的**证书表偏移**，为 0 就是没有内嵌签名。

16. **判定顺序有个刻意的取舍**：内嵌签名**存在但验证失败**时，
    **不再去查目录签名**。否则一个签名被篡改的文件，只要恰好被某个目录收录过，
    就会被**洗白成「签名有效」**。

17. **第一版写错了提前返回** —— 「先取签名者名字，取不到就直接判定为未签名」，
    导致所有文件都可能被误判。**权威结论只能来自 `WinVerifyTrust`，名字只是附加信息。**

18. **`X509Certificate.CreateFromSignedFile` 在 .NET 9 起过时且无等价替代品。**
    改用 `WTHelper*` 从 WinVerifyTrust 的验证状态里直接取证书 ——
    不仅去掉了过时 API，目录签名文件的签名者名字也能取到。

### v1.2.0（IP 归属查询）的坑

19. **给用户用的 `.cmd` 里写中文会直接废掉脚本** —— `cmd.exe` 按系统 ANSI 代码页解码批处理文件，
    UTF-8 中文变成乱码，`REM` 注释被拆成命令，报一串
    `'这是乱码' 不是内部或外部命令`。**`chcp 65001` 救不了**（文件已被解析完）。
    修法：`.cmd` 一律纯 ASCII，用 `ASCIIEncoding` 生成。和 `.ps1` 的 BOM 坑同一类，
     **我又踩了一遍**（而且我自己刚在脚本注释里写了「必须纯 ASCII」）。
20. **数据源选择必须实测，不能凭印象**（这是本版最有价值的一条）：
    - 反向 DNS（PTR）：命中率实测 **25%**（40 个地址中 10 个），
      换成阿里 / DNSPod / 114 / Google / Cloudflare **命中集合完全相同**，换解析器一个都不会多；
    - RDAP（RIR 权威）：覆盖 **75%**，失败的全是本机不通的 `rdap.arin.net` 地址段（AWS / Microsoft）；
    - Team Cymru WHOIS：覆盖 **100%**，国家字段与 RDAP 在 9 个重叠 IP 上 **9/9 一致**。
    结论：**先量再定**，不要因为「反向 DNS 听起来能拿到域名」就开工。
21. **审计口径要跟着能力一起改，否则会变成假报告** —— 原来的检查是「网络类型必须为 0」。
    加了联网能力后，如果只是把这条断言删掉，审计就失去意义。
    正确做法：改成「**全部落在预期清单内**」+ **补一项原生模块的防绕过检查**
    （只看托管类型的话，用 `ws2_32` 就能绕过去）。
    **审计的可信度比审计的绿灯更重要。**
22. **「默认开启」会强制带出「必须能持久关闭」** —— 开关不落盘的话，用户关掉、重启又被打开，
    他对隐私的选择被静默回滚。所以加了 `settings.json`（只存布尔值、原子写入）。
    这两件事必须一起想。
23. **「数据与隐私」面板原来是固定高度 214 + 绝对坐标** —— 隐私文案一加长就会压住下面的开关。
    这是 §4.3 铁律 1 点名的结构。改法：文字放进 `Dock=Fill` + `AutoScroll`，
    固定高度的开关用 `Dock=Bottom` 钉住，结构上不可能重叠。
    **验证方式**：把真实文案复制三遍当「超长文字」，断言不相交 + 渲染图片看。
24. **临时 harness 会写真实的用户数据目录** —— harness 反射构造真实窗体，
    于是会真的写 `settings.json` 和日志。正常结束 `finally` 能清理，
    **但被强杀时会漏**。实测漏了一次，残留的 `settings.json` 里
    `IpOwnershipNoticeShown: true` 会让用户的第一次运行**看不到一次性告知**。
    教训：验证完要**检查 `%LOCALAPPDATA%\WinAppGuard\` 是否干净**。
25. **「按主机名连接」隐含一次 DNS 查询** —— `TcpClient.ConnectAsync(host, port)` 会先解析
    `whois.cymru.com`。这一步在托管元数据里看不到（没有引用 `System.Net.Dns`），
    所以**审计输出和文档都主动写明了** —— 审计扫不到不等于不存在，不能装作没有。

### v1.3.0 的坑（搜索 / 排序 / 列宽 / 临时阻断）

26. **「开机时长」会骗人 —— Windows 的「快速启动」**（用户实测报的）：
    「阻断到下次重启」第一版用「现在 − `Environment.TickCount64`」推算开机时刻来判断是否重启过。
    实测**失效**：用「关机 → 开机」时内核从休眠文件恢复，**开机时长不归零**，
    推出来的开机时刻和上次一模一样 → 判定成「没重启过」→ 规则永远不解除。
    而现象上「托盘图标确实出现了」（登录与自启都正常），正好说明了这一点。
    **修法**：再加一个确定无疑的信号 —— **本次进程是不是被「登录触发的开机自启」拉起的**；
    两个信号命中任意一个就算过期。
    **教训：判断「系统重启过没有」时，不要只依赖一个时间推导值。**
27. **「程序自己发起的后续操作」也要事先同意**：临时阻断到期会自动删规则，
    而项目的硬性约定是"所有会改系统状态的操作必须弹确认框"。自动删除没法再弹框
    （弹了后台程序永远解不开），所以把同意**前置到创建时**。
28. **`Fill` 列右边那条分隔线天生拖不动**（用户实测报的）：
    `AutoSizeMode = Fill` 的列宽度是算出来的、不是固定边界，所以它的右边缘不可拖。
    放在中间就出现「别的线都能拖、唯独那条拖不动」。**修法：Fill 列放最后一列。**
    （另一个反直觉的实测：**去掉 Fill 列反而更慢** —— 会触发横向滚动条反复开关。）
29. **`DataGridViewColumn.Resizable` 会跟着网格的总开关走**：为了关掉「自带实时列宽拖动」
    而设 `AllowUserToResizeColumns = false` 之后，`column.Resizable` 会返回 `False` ——
    命中判断里顺手检查它，就会把**自己实现的拖动也一起关死**
    （现象：鼠标事件送达正常、命中测试也对，但拖动永远不开始）。
    这条是靠**用真实鼠标消息驱动**的断言才发现的。
30. **`Button.PerformClick()` 在控件不可见时静默地什么都不做**：写"清除搜索"的断言时，
    当前若停在别的标签页，`PerformClick` 会点了没反应 → 断言得到一条**假失败**。
    测之前先切回那一页。
31. **规则说明有 255 字符上限**：到期时间写在说明字段里，所以**截断时必须优先保住到期标记**——
    否则长路径会把标记挤掉、规则变永久，用户永远等不到解除还不知道为什么。
32. **定期任务不要放界面线程**：过期检查要枚举全部防火墙规则，实测本机 735 条要 **46ms**，
    挂在界面线程上每 30 秒就有一次可见卡顿。改后台线程之前先验证了
    「COM 对象从 MTA 线程可用」（实测可以）再动手。
33. **「每 3 秒自动刷新」默认是关的**：产品负责人最初打算把到期检查搭在那个刷新循环上，
    但那样**没勾开关的用户永远等不到自动解除**。凡是"定期要做的事"都要想清楚
    依赖的那个开关在默认状态下是不是开着。

### v1.3.0（严格模式）的坑

34. **「改了系统级设置」和「改了规则」是两种性质的东西**：规则改错了点一下就回来；
    而「默认出站动作」是系统级设置，**不随程序退出而恢复**。所以严格模式的规矩完全不同：
    **先落盘意图、再动系统**（先把"我开了"写进 `settings.json`，然后才改防火墙），
    并且**三条还原路径必须齐**（正常退出 / 崩溃后的启动兜底 / `--cleanup` 与「删除全部规则」）。
    **教训：任何"改了不会自己恢复"的设置，先回答"程序没跑完就死了怎么办"。**
35. **`--cleanup` 与「删除全部规则」必须先把严格模式关掉，而且顺序不能反**：
    它们会把白名单删光，而"默认阻止 + 没有白名单"= 整台机器断网。
    先还原、再删规则；反过来的话中间那一瞬间就是断网。
36. **护栏要分清方向**：`ProtectedProcesses` 的原始理由是"拦掉它你就没法用界面解除了" ——
    这只对**阻止**成立。放行永远不会把用户锁在外面，而严格模式**必须**能放行本程序自己
    （否则它连 IP 归属都查不了）。所以护栏改成只对阻止生效，并补了一条反向断言。
    （这个坑是 `--strict-mode-test` **实测撞出来**的，不是想出来的。）
37. **`**` 在 WinForms 里会原样显示**：代码注释里到处用 `**` 表示重点，顺手写进字符串之后，
    用户看到的就是两个星号（Label / 按钮 / 悬停提示都不做 Markdown 渲染）。
    这个坑是**渲染 PNG 时人眼**发现的 —— 于是加了一条自检：扫一遍整个控件树
    （含列头、单元格悬停提示、右键菜单、托盘菜单），发现 `**` 就失败；
    并且**故意塞一个回去验证过它真的会失败**。
38. **"默认阻止"不等于"白名单"**：Windows 自带的允许规则、别的软件建的允许规则**仍然会放行**。
    所以「放行」列刻意分三档（`已放行·本工具` / `已放行·其它来源` / `未放行`），
    把"白名单其实不完整"直接摆在用户眼前，而不是让他以为"只有我放行的能上网"。
39. **界面文案的诚实性要靠"把真实文字拿出来断言"**：严格模式的说明文字抽成了**纯函数**
    （不读防火墙），这样自检才能断言"会话级 / 退出即还原 / 挡不住别人的规则"这些底线
    有没有被改掉。**凡是"我们必须说清楚"的话，都值得抽成可断言的东西。**
40. **COM 的索引属性要先实测再写代码**：`DefaultOutboundAction` 是"按网络配置文件"索引的属性，
    **写回去的语法能不能生效**不能靠猜 —— 先写个自检把它写进去再读回来。
    （实测结论：能写、而且确实是按配置文件存的；被拦时是**立刻** `AccessDenied` 而非超时。）

### v1.4.0（命令行模式）的坑

41. **`WinExe` 的 exe，shell 根本不等它结束**：命令行模式最初就是图形界面程序，
    实测 `--list-blocked` 立即返回、输出错位、`$LASTEXITCODE` 拿不到；
    连着敲几条命令还会**并发** —— 于是 `--list-blocked` 看不到刚建的规则、
    重复 `--block` 也不认幂等。**教训：要给 GUI 程序做 CLI，就得改成控制台子系统**
    （代价是图形界面启动带出控制台窗口）。别想着"反正能输出就行"。
42. **`start /wait` 不带 `/b` 会给子进程开一个新控制台**：试过用 `.cmd` 包装器
    （`start /wait "" app %*`）来绕开上一条，结果**子进程的输出回不到调用方**
    （实测输出行数 = 0）。加 `/b` 才继承同一个控制台。最后选了控制台子系统，
    包装器就没发布 —— 这条留着，以后有人想用包装器时能省一次踩坑。
43. **改了 `OutputType` 必须清 `obj/bin`**：`dotnet publish` 直接跑会复用旧的 apphost，
    **PE 头里的子系统不会更新** —— 表现是"明明改了 csproj，exe 还是旧行为"。
    验证方法：读 PE 头 `OptionalHeader` 偏移 68 处的 `Subsystem`（2=GUI，3=Console）。
44. **控制台窗口的可见时长 = 进程启动时间**，不是"闪一下"：单文件自包含 exe 启动；
    实测稳态约 0.55 秒，而发布后**第一次**运行因为 Defender 要扫这 49MB 的新文件，
    实测 **11.2 秒**（对照自检工具：首次 9.4 秒 → 之后 185ms）。
    所以"改子系统"这种决定，必须拿**实测数字**去让产品负责人拍板，不能凭"闪一下"这种描述。

### v2.0（WFP）的 POC 结论（2026-10-17，一次性实验，不进仓库）

用 `WfpProbe.exe`（临时工具）在 VMware 虚拟机里实测，四个问题全部有答案：

1. **引擎 / sublayer / filter 的 interop 通路打通** —— 最小实现（开引擎、建 sublayer、
   filter 增删、枚举、取程序身份）**251 行**（10 个函数 + 8 个结构体）。
2. **WFP 的 block 能压过 Windows 防火墙的 allow** ✓ —— 我们自己的 sublayer 用权重 `0xFFFF`，
   实测：加 WF allow 规则后能连通 → 再加我们的 WFP block → **连不上** → 删掉后又通。
   **结论：2.0 做"默认拒绝"不需要改全局默认动作**（1.3 那个风险点消失）。
3. **动态会话（`FWPM_SESSION_FLAG_DYNAMIC`）的过滤器随进程消失** ✓ ——
   实测：子进程挂上 block（1 条，连接被拦）→ **任务管理器式强杀** → 过滤器变 0 条、连接恢复。
   **结论：临时阻断 / 严格模式可以做到"退出即撤销"，不需要任何还原逻辑。**
4. 两个**必踩的坑**（都靠实测才发现，文档里没写清楚）：
   - **`providerData` 是 `FWP_BYTE_BLOB` 结构体本身，不是指针** ✗ ——
     写成 `IntPtr` 会让后面所有字段错位 8 字节，报 `FWP_E_INVALID_ENUMERATOR (0x8032001D)`；
     `FWPM_FILTER0` 正确大小是 **200**、`FWPM_SUBLAYER0` 是 **72**。
   - **`action.type` 必须带 `FWP_ACTION_FLAG_TERMINATING (0x1000)`** ✗ ——
     只写 `FWP_ACTION_BLOCK (0x1)` 会被拒，报 `0x80320024`（"该操作类型不是筛选器允许的操作类型"）。
     证据：系统自带过滤器的 `action.type` 是 `0x00001002`（PERMIT|TERMINATING）。
     所以 BLOCK = `0x00001001`，PERMIT = `0x00001002`。
   - **`FWPM_ACTION0` 是 20 字节，不是 24**：GUID 在 Windows 上的对齐是 **4**，不是 8，
     所以 `FWP_ACTION_TYPE(4) + GUID(16)` 不会填充到 24。
     （搬到产品时 `EnsureLayout` 第一次运行就把这个期望值错误抓了出来 —— 这道保险值得留。）
   - **过滤器与子层的生存时间必须兼容**：把**持久化过滤器**挂到**非持久化子层**上，
     WFP 报 `FWP_E_INCOMPATIBLE_TXN (0x80320016)`（"该调用尝试将两个生存时间不兼容的对象相互关联"）。
     所以 `WfpRuleStore` 里过滤器的持久化是**跟随子层实际状态**（`WfpEngine.SublayerPersistent`），
     而 `EnsureSublayer` 遇到"已存在"必须**读回**真实状态，不能沿用调用方的假设。
   - **"写入成功但读回 0 条规则" = 说明字段没写进去**：`FWPM_FILTER0.displayData`
     有 `name` 和 `description` 两个指针，只设了 `name` 就会是这种现象（过滤器在、
     但规则内容不在）。自检里加了一条断言专门钉住它。

5. **persistent filter 熬得过重启** ✓ —— 实测：加两条（一条带 `FWPM_FILTER_FLAG_PERSISTENT`、
   一条不带）→ **真重启虚拟机** → 带标志的还在（1 条），不带的消失。
   **结论：2.0 的"永久阻止"可以直接靠 WFP 持久化，不需要自己的规则库、也不依赖开机自启。**
   （`mpssvc` 服务不允许停止，所以"跨重启"验证只能真重启，不能用 `net stop mpssvc`。）
6. 还有个**结构体之外**的坑：`FWPM_CONDITION_IP_PROTOCOL` 的 GUID 当时写错了，
   报 `FWP_E_CONDITION_NOT_FOUND (0x80320002)`（"筛选条件不存在"）。
   真要做端口/协议级规则时，**必须从官方文档核对每个条件字段的 GUID**，不能凭记忆。
7. 清理顺序：**先枚举并删光我们 sublayer 里的所有过滤器，再删 sublayer**。
   漏删任何一条都会报 `FWP_E_IN_USE (0x8032000A)`。

**尚未验证**（2.0 开工后要补测）：360/火绒 等装着自己 WFP 过滤器的环境下的行为（不阻塞开工）；
WFP 枚举在 400+ 条时的耗时（影响界面刷新体验）。

**2.0 的设计因此定为**：严格模式 = **动态会话**（崩溃即自动撤销）+ 白名单 permit；
临时阻断 = **持久化 filter + 说明字段里的到期标记**（语义与 1.3 一致，不随程序退出提前解除）。

## 2.1 前置 POC：WFP 网络事件（2026-10-18，一次性探测，不进仓库）

用一次性工具 `WfpNetEventProbe.exe` 在虚拟机里实测，结论如下：

**1. 订阅可用**：`FwpmNetEventSubscribe0` 成功。
结构体尺寸：`FWPM_NET_EVENT_SUBSCRIPTION0` = **32**、`FWPM_NET_EVENT_HEADER1` = **144**、
`FWPM_NET_EVENT1` = **160**。除了总尺寸，还必须断言**字段偏移**（见坑 2）。

**2. ★ 被放行的连接不产生事件**：订阅期间建立一条成功的出站连接，收到 **0 条**事件。
所以 2.1 的审计数据源只能是：
- **正常连接** → 沿用现有 3 秒轮询（会漏短连接，如实写进文档）；
- **被拦的连接** → 网络事件（轮询根本看不到）。

**3. 被拦事件的内容够用**：实测一条 block 触发 2 条 `CLASSIFY_DROP`（connect 会试多个 A 记录），
每条都带：`appId`（进程身份）、真实的本地/远端 IP 与端口、`flags`、
**`filterId`（就是我们自己那条过滤器的 ID → 可以回答"被哪条规则拦的"）**、`layerId`。

**4. 两个会静默读错数据的坑**（都不会崩溃，只会显示垃圾）：

- **地址联合体的对齐**：C 里它由 `UINT32` 和 `byte[16]` 组成，对齐是 **4**；
  在 C# 里如果写成 `ulong` 字段，.NET 会把对齐算成 **8**，整个地址/端口区偏移 4 字节。
  症状非常迷惑：**`appId` 仍然正确**（后续填充恰好抵消），但地址读出来是 `0.0.0.0:0`。
  做法：把联合体定义成 4 个 `uint`（`Size = 16`），并对每个字段做 `Marshal.OffsetOf` 断言。
- **IPv4 字节序**：直接 `new IPAddress(addr.V4)` 会得到字节反转的地址
  （`192.168.36.135` 显示成 `135.36.168.192`）。
  做法：按**内存原始字节**（网络序）构造 `IPAddress`。

**待办**：POC B —— ETW `Microsoft-Windows-DNS-Client`，决定"域名归属"的准确度。

### 2.1 POC B：ETW DNS —— **未成功**（2026-10-18）

- **能建立会话**：`StartTrace` / `EnableTraceEx2` 都成功。
- **消费端崩**：`OpenTrace` + `ProcessTrace` 稳定触发 **0xC0000409**（fast fail），
  进程直接消失、没有托管异常栈。

  按天分文件、**按体积分段**（默认 8 MB）、保留 **7 天**、每条追加即刷盘。
  写失败只累计计数、不抛异常（审计不能影响主功能）。
- 两个实测坑：
  1. **读写必须共享**：写端用 `FileShare.Read` 时，读端（`File.ReadLines`）会因
     共享模式不包含写而报 IOException —— 表现为"明明写了，读回 0 条"；
     两端都改成 `FileShare.ReadWrite` 才对。
  2. **断电半行**：最后一行可能是半截 JSON，解析失败直接跳过，不影响其它记录。
- 自检 `--audit-store-test`：**18 项全通过**
  （往返 / 中文路径 / IPv6 / 半行容错 / 轮转 5 个分段 / 保留期 / 关闭记录 / 清空 / 摘要）。

**下一步**：DNS 缓存快照（`DnsGetCacheDataTable` + 缓存内查询）+ 域名索引，
然后是 WFP 网络事件采集器与界面面板。

**第 2 步（DNS 缓存 + 域名索引）已完成**：

- `Core/Audit/DnsCacheReader.cs` —— 读 **Windows DNS 客户端的内存缓存**：
  `DnsGetCacheDataTable` 枚举名字，`DnsQuery(DNS_QUERY_NO_WIRE_QUERY)` **只读缓存、不发包**。
  不新增任何外部端点。
- `Core/Audit/DomainIndex.cs` —— IP → 候选域名（带 30 分钟有效期）：
  单候选 = 高置信；多候选 = 全部列出（CDN 撞车）；没有记录 = null。
- 两个实测坑：
  1. **`DnsGetCacheDataTable` 成功时返回 1，不是 0**。按"非 0 即失败"处理会直接丢掉整张表
     （表现为"缓存明明是满的，却读到 0 条"）。只以**表指针是否有效**为准。
  2. DNS_RECORD 的 Data 在**偏移 32**，且必须按**原始字节**读（和 WFP 地址那次同一个教训）。
- 自检 `--audit-dns-test`：**12 项全通过**（真实缓存 7 条、单/多候选、过期、IPv6、索引一致性）。
- 实测到的真实缓存特征：TTL 有 **0~1 秒**的条目（`steamserver.net` 的 4 个 IP），
  说明**必须高频快照**，否则根本抓不到 —— 这条直接决定了采集器的轮询间隔（2~5 秒）。

**第 3 步（采集器）已完成**：

- `Interop/WfpNetEventNative.cs` —— 网络事件的互操作（含**字段偏移**断言）。
- `Core/Audit/WfpDropCollector.cs` —— 订阅 `CLASSIFY_DROP`，解析出
  进程路径 / 远端 IP:端口 / 协议 / **filterId**（可对应到规则）/ layerId。
- `Core/Audit/DevicePathMapper.cs` —— 把 `\device\harddiskvolumeN\...`
  映射成 `C:\...`（`QueryDosDevice`，长前缀优先）。
- `Core/Audit/ConnectionTracker.cs` —— 连接**差集**：长连接只记一次，
  断开重连会再记一次；排除监听、回环、未建立。
- 自检 `--audit-live-test`：本机实测 12 秒采到 **60 条新连接**（chrome / 抖音 / B 站…），
  差集逻辑与设备路径映射通过；非管理员时自动跳过事件订阅。

**第 4 步（AuditService 串联）已完成**：

- `Core/Audit/AuditService.cs`：后台线程把三个数据源串起来并落盘
  （DNS 快照 + 连接轮询 + 拦截事件），每天清理一次过期文件；
  订阅失败（如非管理员）只影响拦截事件，轮询照常继续。
- 自检 `--audit-service-test`：本机 12 秒写入 **59 条**、文件 10.5 KB、
  读回条数与计数一致；其中 **1 条命中域名**（本机缓存里只有 bitdefender 那条长期有效）。
- ⚠️ 实测提醒：**域名命中率取决于缓存里有什么**。本机 59 条连接只命中 1 条域名，
  因为大量连接走 CDN/DoH 或解析记录已过期。这一点必须在界面上如实显示
  （"域名未知"而不是空白），并且不能作为任何自动决策的依据。

**第 5 步（实测修正与全绿）**：

- 发现 `DnsGetCacheDataTable` 会列出**已经过期、但仍挂在表里**的名字；
  对这些名字 `DnsQuery(NO_WIRE_QUERY)` 返回 **9701**（缓存里没有有效记录）。
  实现的选择：**跳过，绝不回退到联网查询** —— 守住"读缓存不发包"的契约。
  代价是域名覆盖率取决于缓存新鲜度，这一点已如实写进文档。
- 自检 `--audit-service-test` 改为**主动造一条可验证连接**
  （先解析 whois.cymru.com，再连上并保持 6 秒），断言收紧到"这条记录必须带域名"。
  实测通过：`216.31.12.15:43 → whois.cymru.com`。
- 辅助修复：DNS_RECORD 读取前校验 `DataLength`，单条坏记录不再影响整轮。

**第 6 步（域名推测改为"缓存优先、可回源"，默认开启 —— 产品负责人确认）**：

- 原因：实测 `DNS_QUERY_NO_WIRE_QUERY` 在本机对**大多数**缓存条目直接返回 9701
  （连 TTL 还有 141 秒的 `www.google.com` 也一样），零发包模式下域名覆盖率只有约 **8%**。
- 改为：`DnsQuery(options = 0)` —— **缓存优先**；条目刚好过期时，
  Windows 可能向**本机配置的 DNS 服务器**补发一次查询。
  仍然**只查缓存表里已经存在的名字**，不会主动解析任意域名。
- 覆盖率实测（本机）：**9 条 → 144 条记录 / 125 个 IP / 30 个域名**；
  服务采样 59 条连接里有 **17 条**带域名（约 29%）。
- 设置项：`AuditDomainLookupEnabled`（**默认开启**）。关闭后回到零发包模式，
  代价是覆盖率回到约 8% —— 这个取舍必须写进《安全说明》。
- 出厂审计里的登记描述已改成事实（不再声称"固定用 NO_WIRE_QUERY"）。
- ⚠️ 这是本项目**第二条会产生网络请求的路径**（第一条是 whois 查询）：
  文档、设置页、隐私说明都必须明确写出"开启域名推测时可能向本机 DNS 服务器发查询"。

## 10. 与项目负责人协作的方式

这些是实际协作下来总结的，照着做能少走很多弯路。

### 工作节奏

- **一次只做一个目标**，做完**停下来**让他验证，不要一口气推好几步。
- 每轮回复的结构他用得比较顺：
  1. 交付物清单（新增/修改了哪些文件，各自干什么）
  2. **实测数据**（不是「应该能行」，是真跑出来的数字）
  3. 需要他做的验证（表格形式，一条一条可勾选）
  4. 下一步
- **他会自己在虚拟机里测**，并且**很擅长找 bug**。不要糊弄 ——
  他没测过的项要如实标注「未验证」。

### 必须主动做的事

- **发现需求冲突或安全风险要立刻提出来，并给出建议方案，等他确认。**
  他明确要求过这一点，而且确实会采纳。
- **踩到坑要写进代码注释说明原因**，不要只是改完就算。
- **自己的推断被实测推翻时要坦白承认**，并把这个教训记进文档。
  项目里已经有几条「我原先以为…实测推翻了」的记录，他认可这种诚实。

### 几个他做过的决定（不要擅自改回去）

- **证书吊销检查默认开启**，接受程序因此产生网络流量。
  （1.2 之后「自身不含网络代码」这个说法也不成立了，见下一条。）
- **IP 归属查询默认开启** —— 与吊销检查同一取舍，但**必须能关、且关得住**
  （关掉后写进 `settings.json`，重启不会自己打开）。同时保留一次性的首次运行告知。
- **否决了离线 GeoIP 数据库** —— 他明确说过「不喜欢离线数据库，觉得会影响准确性」。
  所以数据源走在线（Team Cymru WHOIS），不要擅自改回内置库。
- **否决了 RDAP** —— 实测覆盖率只有 75%（失败的全是被挡的 ARIN 地址段），
  比 Team Cymru 差，且实现更重。
- **归属信息用悬停提示、不加新列** —— 连接表已经有 10 列，再加会出现横向滚动条。
- **行底色用整行染黄**（未签名），不是只标签名格。
- **配色分级**：签名问题=淡红、未签名=淡黄、已阻止=淡蓝；
  优先级「签名问题 > 未签名 > 已阻止」。
- **提交历史一次性提交**，不做按阶段的拆分。
- **代码注释保持中文**，只把 README 写成英文。
- **给用户用的 `.cmd` 保持纯 ASCII**（中文只放文件名和输出），别再往里写中文注释。
- **零依赖是硬线，不为了边角情形引入依赖**：例如「直到下次重启」在
  「没开自启 + 快速启动关机」时判断不出来，要彻底解决只能上 WMI 或事件日志 ——
  **产品负责人明确否决了**，选择把限制如实写进文档。
- **列宽用「预览线」拖动**（拖动时只画一条竖线，松开才真正改宽度）：
  自带的实时拖动每移动一次鼠标就把整表重画一遍，最大化窗口下实测要 33~40ms/帧（25~30fps），
  慢机器上明显卡。**接受「拖动中没有实时预览」这个代价**。
- **`Fill` 列放在最后一列**，不放程序路径上：Fill 列右边那条分隔线天生拖不动，
  放中间会出现「别的线能拖、唯独那条拖不动」。代价是路径列不再自动变宽。
- **搜索与排序都不持久化**（关掉程序就忘）：这样不用动
  `settings.json`「只存布尔值、不存 IP / 进程名 / 路径」那条既有约定。
- **临时阻断到期自动解除 + 弹一次托盘气泡**：不声不响地解除会让人困惑
  （「这程序怎么又能联网了」）；同意在**创建时**取得（确认框里的「阻断时长」）。

## 14. 2.1.2：黑名单 / 严格模式下白名单（2026-10-18）

### 为什么拆

一张「规则」表同时装**阻止**和**允许**，带来三个说不清：

1. 按钮名字说不清：「允许选中程序联网」听起来像"新建一条允许规则"；
2. 操作后果说不清：删掉一条到底是"解除阻止"还是"把它踢出白名单"；
3. 生效条件说不清：白名单**只在严格模式下**有意义，却和随时生效的黑名单混在一起。

### 结构

| 页签 | 内容 | 操作 |
|---|---|---|
| 黑名单 | `Action == Block`：程序阻止 + 封禁 IP，带「类型」列 | 删除选中 / 清空黑名单 |
| 严格模式下白名单 | `Action == Allow` | 添加程序… / 移出白名单 / 清空白名单 |

两页各自有搜索、各自清空，互不影响；页签上直接显示数量。

### 决策

1. **白名单页必须有「添加程序…」**：严格模式下没放行的程序**连不上网**，
   因此**不会出现在「联网连接」页** —— 只靠连接页的「加入白名单」会陷入
   "想放行却找不到它"的死循环。这是拆分之后暴露出来的真实缺口。
2. **「解除阻止」只删阻止规则**：原来 `ConfirmAndAllowProgram` 会删该程序的**全部**规则
   （含允许规则），等于顺手把它踢出白名单 —— 那是 1.x 的语义。已修正。
3. **清空黑名单不再需要关严格模式**（白名单已经不在里面了）；
   清空白名单才提示"严格模式正在生效时，这些程序会立刻断网"。

### 自检

- `--ui-polish-test` 25 → **31**（两个页签、白名单添加入口、两处清空按钮、空状态）；
- `--ui-dpi-test` 9 → **12**（白名单工具栏 + 按钮文字宽度）；
- `--render-docs` 新增 `05-whitelist.png`。

## 15. 2.1.3：记录保留期可调（2026-10-18）

### 做了什么

- 「记录」页第一行最右加了 **「记录保留」** 下拉：1 / 3 / 7 / 30 天（默认 7 天）；
- 写进 `settings.json` 的 `AuditRetentionDays`（整数 1–30，非法值回落 7）；
- 改动后**重建审计服务**，`Start()` 里先按新保留期清一次 —— 不然用户把 7 天改成 1 天，
  旧文件要等到下一个零点才消失，看起来就是"开关没用"；
- 状态栏显示当前保留期（`… · 保留 3 天`）。

### 决策

1. **`settings.json` 的"只存布尔值"约定放宽为"布尔值 + 保留天数"**。
   理由是这条约定的**目的**是"不存任何隐私信息"，而一个 1–30 的整数不携带任何隐私；
   自检也相应改成"除 `AuditRetentionDays` 外不允许出现非布尔值"。
   不把天数塞进 `ui-state.json`：它是用户设置，不是界面状态。
2. **保留期是 `AuditStore` 的构造参数**，所以改完必须重建服务；不做"运行中热改字段"，
   那种写法容易让界面显示和实际清理口径不一致。
3. 关掉「记录连接」时下拉框变灰：没有记录在产生时，保留期没有意义。

### 自检

- `--audit-ui-test` 11 → **16**（下拉存在、四个选项、索引↔天数双向映射、默认 7 天、不与「添加 IP」重叠）；
- `--audit-store-test` 20 → **23**（1 / 3 / 30 天对"3 天前的文件"的去留各不相同）；
- `--ownership-core-test` 17 → **19**（保留天数往返、手改成 999 时回落 7）。

### 顺带修回一个 2.1 遗留的测试缺陷

`--audit-service-test` 的「读回条数 == 写入计数」是**测量竞态**：原写法先读计数、再 `Dispose()`，
而 `Dispose()` 会等当前那一轮轮询写完 —— 联网繁忙时必然"读回比写入多"（实测 +2）。
改成 **`Dispose()` 之后再读计数**。这个修复原本在 2.2 分支里，随 2.2 回退一起丢了，现已补回。

## 17. 2.4：规则分组 + 导入导出（2026-10-18）

### 做了什么

## 18. 2.5：精细化规则（协议 / 端口 / 网络位置）（2026-10-19）

### 做了什么

- `RuleScope`：协议（Any/Tcp/Udp）、远端端口（单个或范围）；
- 添加程序时先选范围；规则列表新增「范围」列；同一程序可有多个不同范围的规则；
- 导出/导入包含范围；旧 v1 规则仍可读。

### 关键决策与依据

1. **严格按 WFP 条件实现，不做"界面开关"**：
   - 协议 → `FWPM_CONDITION_IP_PROTOCOL`（FWP_UINT8，6/17）；
   - 远端端口 → `FWPM_CONDITION_IP_REMOTE_PORT`（FWP_UINT16，范围用 `FWP_RANGE` + `FWP_MATCH_RANGE`）；
   GUID 全部从 `fwpmu.h` 抄，并对照了微软官方文档。
2. **端口必须配合 TCP/UDP**：协议为「任意」时 WFP 无法按端口匹配 —— 界面直接拦住并说明原因，
   而不是生成一条"看起来设了端口、实际不生效"的规则。
3. **范围标记看不懂就不认这条规则**：v2 说明里第 6 段解析失败时 `TryParse` 返回 false，
   该规则不会出现在界面里，也就不会被误删。
4. **规则名带范围后缀**（`_tcp443` / `_udp8000-8100` / `_tcp443-pub`）：
   同一程序的不同范围规则不能重名，否则会互相覆盖（过滤器 key 也把范围算进去了）。

### 自检

- `--rule-scope-test`（**20 项**，离线）：编码往返 / 非法组合 / 端口文本 / v1+v2 说明 / 规则名 / 旧 4 段标记兼容 / 导出含范围；
- `--wfp-scope-test`（**3 项**，需管理员，**必须在虚拟机里跑**）：
  只拦 43 端口时 43 被拦、443 仍通、删除后恢复。

### ⚠️ 网络位置：做过，然后**删掉**了

开发期确实实现了 `FWPM_CONDITION_CURRENT_PROFILE_ID`（0=公用 / 1=专用 / 2=域，值域来自
`netlistmgr.h` 的 `NLM_NETWORK_CATEGORY`），BFE 也接受这条过滤器。
但**虚拟机实测：只有「任意网络」能拦住；指定公用 / 专用时不生效**。

结论：**不做这个功能**。界面、模型、导出格式里的网络位置字段全部移除，
只保留协议 + 端口。留着它就是"看起来设了、其实不生效"的假开关。
为兼容开发期建过的规则，解析时仍接受旧的 4 段标记（如 `tcp-443-443-any`），
但忽略最后一段、只按前三段理解。

## 23. 3.0-c（切片 1）：严格模式归服务（2026-10-22）

### 为什么先做这个

严格模式是"自保"的核心：**保护不能跟着界面一起消失**。
2.x 的严格模式会话活在界面进程里，关掉界面 = 限制消失，而用户以为它还在。
3.0-c 把动态会话搬进服务：

- 界面关掉 → 保护仍在；
- 服务被停 / 崩溃 → 动态会话随进程消失，**立即撤销**（安全方向，不会留下
  "所有人都上不了网且没人能关"的死局），服务随后按失败策略自动重启；
- 开启 / 关闭必须提权（`write.strict.*`），普通用户不能"一键关保护"。

### 实现

- 服务端 `StrictModeHost`：包住 `StrictModeManager`，所有调用串行化；
  - 额外放行 **界面 exe**（`<安装目录>\WinAppGuard.exe`，否则严格模式下界面查不了 IP 归属）；
  - 服务自己由 `StrictModeManager` 自动加入；
  - 写白名单（加/删/清空/导入）后自动重建会话；
  - `ControlServer.Stop()` 主动撤销会话（崩溃时由 BFE 自动撤销）。
- `System.Threading.Timer` 每 30 秒清理到期临时规则（界面关着也生效；3.0-b 的缺口补上）。
- 协议：`rules.allowTargets`（替界面读"谁被放行"）、`write.strict.enable/disable/refresh/
  recoverLegacy`；`ServiceStatus` 增加 `StrictModeActive` / `StrictModePermittedCount`。
- 界面：开关、状态、放行清单全部走 IPC；服务不可用时严格模式按钮禁用并写明"不可用"。
- 1.x 遗留兜底（还原被改过的默认出站）：
  - 安装 / 修复时由 `WinAppGuardSetup.exe` 以当前用户身份执行；
  - 服务也提供 `write.strict.recoverLegacy`（界面把 settings.json 路径传过去），
    覆盖"没重装、直接开界面"的情况。

### 自检

- `--service-strict-test`（8 项，需管理员 + 服务已运行）：IPC 开启 → 过滤器进入 BFE →
  停服务 → 过滤器全部消失 → 重启服务 → 状态复位。
- `--ui-offline-rules-test` 扩到 11 项：离线时严格模式开关禁用、说明写"不可用"。
- 本机：构建 0 警告 0 错误；ui-check 240/240；离线只读 11/11。

### 待 VM 验收

1. `--service-strict-test`（**会短暂停/启服务**）8/8；
2. 界面开启严格模式 → 关掉界面 → 未放行程序仍上不了网；
3. `services.msc` 停止服务 → 网络立即恢复（严格模式撤销）→ 启动服务 → 界面显示未开启；

## 26. 3.0-c（切片 3）：审计迁移（2026-10-22）

### 目标

- 采集与落盘都在服务：**关掉界面记录继续**；
- 记录文件从用户目录搬到 `%ProgramData%\WinAppGuard\audit`；
- 界面只读记录 + 通过 IPC 改设置（开关 / 域名推测 / 保留期）与清空；

### 实现

- `AuditHost`（服务）：持有 `AuditService`，随服务启停；设置存
  `%ProgramData%\WinAppGuard\audit-settings.json`（机器级）。
- 新 IPC 命令：
  - `write.audit.configure`（AuditEnabled / AuditDomainLookup / AuditRetentionDays，null = 不改）；
  - `write.audit.clear`（服务先停采集 → 删文件 → 按原设置恢复）。

  AuditRetentionDays / AuditEventsWritten。
