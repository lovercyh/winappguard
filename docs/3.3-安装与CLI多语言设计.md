# 3.3 安装器 / CLI 多语言与服务日志设计

> 状态：已实现（2026-10-24）。
> 范围：安装器与卸载器固定中英双语；CLI 默认跟随 GUI 已生效语言并支持 `--lang`；
> 服务日志固定英文 + 稳定事件码；GUI 日志跟随界面语言。
> **不做**：WFP DACL 变更、自动更新、协议/服务/所有者模型变更、安装器语言开关。

## 1. 为什么这样分工

三个位置的生命周期完全不同，所以不能套用同一种语言策略：

| 位置 | 生命周期 | 谁会看到 | 3.3 策略 |
| --- | --- | --- | --- |
| 安装器 / 卸载器 | 几十秒，装完就退出 | 中文用户、英文用户、看不懂系统语言的人 | **固定双语并列**，不做开关 |
| CLI | 每次命令独立进程 | 脚本和终端用户 | 默认跟随 GUI；`--lang` 单次覆盖 |
| 服务日志 | 长期落盘、常被复制去排障 | 排障者、未来的自己 | **固定英文 + 事件码**，不跟随 GUI |
| GUI 日志 | 长期落盘、按用户分目录 | 当前用户、排障者 | **跟随界面语言**（中文界面中文，English 界面英文） |

安装器如果跟随 GUI 语言，就会遇到「还没装好，哪来的界面语言」的死循环；
服务以 SYSTEM 运行，没有「当前用户界面语言」这个概念；CLI 则是用户当场在用的工具，
跟随 GUI 最符合直觉。这是三套策略的由来。

## 2. 安装器 / 卸载器

### 2.1 输出规则

- 短状态行：`中文  |  English` 同一行（`Bilingual.Say`）。
- 警告 / 错误 / 长说明：中文一行、英文一行（`Bilingual.Fail`）。
- 帮助文本：中文整段 + 空行 + 英文整段，两种语言各自完整，不来回穿插。
- 卸载确认清单：中文清单 + 英文清单，最后一行同时给出两种语言的 `[y/N]` 提示。

实现位置：

- `src/WinAppGuard.Setup/Bilingual.cs`：`One` / `Say` / `Fail`。
- `src/WinAppGuard.Setup/Program.cs`：所有面向用户的输出都走这两个入口。

### 2.2 不做语言开关的原因

安装器需要先于任何设置运行，而 `ui-state.json` 属于某个用户、且安装器可能由
另一个提权账户运行。固定双语没有状态、不会读错文件、也不会在修复/卸载时
因为语言设置缺失而报错。

### 2.3 边界

- 服务显示名 / 服务描述（`services.msc` 里看到的文本）仍由 `ServiceProtocol` 决定，
  本次不改：它属于产品标识，不是安装器输出。
- 系统返回的本地化错误文本不会被翻译；安装器只保证**自己的说明文字**双语。

## 3. CLI 语言

### 3.1 优先级

```
--lang zh|en|auto  >  ui-state.json 的 AppliedLanguage  >  系统 UI 语言（auto）
```

- `--lang` 只影响本次进程，不写任何文件。
- 未传 `--lang` 时读 GUI 已生效语言；GUI 从未运行过则回退 `auto`。
- `auto` 的解析与 GUI 相同：中文系统 → 中文，其它系统 → English。
- 非法 `--lang`（例如 `fr`）直接报错退出码 1，不静默回退。
- `--lang` 可以放在命令前后任意位置，也接受 `--lang=en` 写法；大小写不敏感。
- 参数错误提示跟着 `--lang` 走（`--lang en` 时错误也是英文）。

实现位置：

- `src/WinAppGuard.Core/Localization/CliLanguage.cs`：纯函数，可自检。
- `src/WinAppGuard.Core/Localization/UiLanguageStore.cs`：只读 `ui-state.json`。
- `src/WinAppGuard.Svc/Program.cs`：`--cli` 分支解析 `--lang` 并初始化共享 `Localizer`。

### 3.2 `AppliedLanguage` 的意义

`ui-state.json` 里同时有：

- `Language`：用户的选择（下次启动生效）；
- `AppliedLanguage`：GUI **本次真正生效**的语言。

GUI 启动时把 `Language` 写进 `AppliedLanguage`。这样「用户刚切成英文但还没重启」时，
CLI 仍然使用旧语言 —— 与用户眼前看到的界面保持一致。

旧版（3.2）文件没有 `AppliedLanguage`，读取时回退 `Language`，不需要迁移脚本。

### 3.3 数据契约（不能变）

`--list-blocked` 的规则行永远是：

```
规则名<TAB>程序路径<TAB>到期信息
```

- 1 行 1 条，Tab 分隔，`#` 开头为说明行；
- 翻译只允许改标题、表头、注释、帮助和错误提示；
- 规则名、路径、列顺序、分隔符在所有语言下完全一致。

到期信息在英文下是 `Permanent` / `Until next restart` / `Timed`；
中文仍是原有的自然语言描述。

## 4. 服务日志

### 4.1 格式

```
2026-10-24 12:34:56.789 [INFO] [WAG-SVC-002] Service started.
```

- 级别固定为 `INFO` / `WARN` / `OP` / `ERROR`；
- 每条日志都带稳定事件码 `[WAG-<类别>-<三位编号>]`；
- 主行只写英文；
- 异常另起若干行，只写：

```
exception=System.ComponentModel.Win32Exception hresult=0x80004005 nativeErrorCode=5
   at ...
```

**不写 `Exception.Message`**：系统异常的 Message 会跟随系统语言，一旦写进去，
英文日志就会混入中文。类型、HResult、Win32 错误码和堆栈已经足够定位问题。

实现位置：

- `src/WinAppGuard.Svc/ServiceLog.cs`：事件码格式、异常描述。
- `src/WinAppGuard.Core/LocalLog.cs`：`English` 开关把级别名映射为英文，
  并让共享层（WFP/审计/严格模式）写入的日志同样使用英文级别和英文异常描述。
- `ServiceLog.Initialize` 打开 `LocalLog.English`；GUI 日志不受影响。

### 4.2 GUI 日志（跟随界面语言）

- `LocalLog.English` 在 GUI 启动时按 `Localizer.IsEnglish` 设置；切换语言需要重启，
  所以一次进程生命周期内日志语言是稳定的。
- 每条 GUI 日志用 `LocalLog.Pick(中文, English)` 成对写入；English 界面不会出现中文主行。
- 级别名同样跟随：中文 `[信息] / [警告] / [操作] / [错误]`，英文 `[INFO] / [WARN] / [OP] / [ERROR]`。
- 英文模式下异常只写类型、HResult、Win32 错误码和堆栈，不写本地化的 `Message`。
- 服务返回的中文提示不会进入英文日志主行（例如严格模式只记 `ok=true/false`）。
- 共享层 `RuleGroupStore` 也走 `Pick`；服务进程里 `English = true`，所以服务日志仍是英文。

## 5. 自检

新增两个离线自检：

| 模式 | 覆盖 |
| --- | --- |
| `--cli-language-test` | `--lang` 优先级、`AppliedLanguage` 读取与回退、英文帮助、数据行三段契约、中英文前两段一致 |
| `--log-format-test` | 英文级别、事件码保留、异常不写本地化 Message、`Pick` 中英文选择、关掉英文模式后恢复中文级别 |

两者都不需要管理员权限、不写系统状态。

## 6. 已知边界

- 服务显示名/描述仍是原样，不随语言变化。
- 迁移明细、系统错误文本等「数据」可能含中文；服务日志只保证**自己写的主行**为英文。
- `LocalLog.English` 打开后，共享层（WFP/审计/严格模式）写入服务日志的行也变为英文；
  GUI 自己的日志目录不受影响。
