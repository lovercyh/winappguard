## 0. 一句话状态

WinAppGuard 是一个 Windows 图形界面的防火墙规则管理工具，已开源发布到 **v1.1.0**，
仓库 <https://github.com/lovercyh/winappguard>，CI 绿、文档齐、无已知缺陷。

---

## 1. 项目是什么

**它本身不拦截任何流量**，真正生效的是 Windows 防火墙。它只负责：

- 列出当前正在联网的 TCP 连接（从「谁在联网」入手，而不是翻程序列表）
- 按程序路径创建 / 删除出站防火墙规则（规则名一律以 `AppGuard_` 开头）
- 检查程序的**数字签名**（内嵌签名 + 目录签名两条路径都查）
- 可选的系统托盘 + 开机自启（任务计划程序）

**关键差异化**：它提供**可验证的信任** —— `--audit` 模式直接读编译产物的元数据，
证明零第三方库、程序自身零网络代码、只有 16 个原生调用。同类工具里少见。

## 4. ★ 必须遵守的约定（破了会出问题）

### 4.1 语言与风格

- **代码注释、提交信息、Issue、PR 全部用中文。** 对外 README 是英文，但代码注释是中文，
  混进英文注释会让整个文件读起来割裂。
- **构建必须 0 警告 0 错误。** 警告在这个项目里当缺陷处理，CI 用 `-warnaserror` 卡住。
- 不引入第三方库。能用 BCL 解决就用 BCL。
- 注释要解释**为什么**，不是**做什么**。代码本身说明做了什么。

### 4.2 安全红线（安全边界，改动需要特别说明理由）

1. **只创建和删除 `AppGuard_` 前缀的规则** —— `FirewallManager.DeleteRule` 里有硬性校验，
   不要把校验挪到界面层。
2. **绝不修改全局防火墙策略** —— 代码里不存在写入 `FirewallEnabled` /
   `DefaultInboundAction` / `DefaultOutboundAction` 的路径。
3. **关键进程保护做在防火墙底层**（`FirewallManager.ValidateProgramPath`），不能只做界面置灰。
4. **不用注册表做持久化** —— 开机自启只用任务计划程序。
5. **日志只写本机，不上传任何内容。**
6. **所有会改系统状态的操作必须走 `ConfirmForm` 弹确认框。**

### 4.3 ★ 界面布局的三条铁律（每一条都是踩过坑换来的）

1. **用 Dock 布局，不要用「`AutoSize` 控件 + 绝对坐标 + 固定高度容器」。**
   后者在文字长度会变化的地方**必然**出问题 —— 「开机自启」详情区因此压住过下面的按钮
   （用户实际报的 bug）。
2. **`AutoScroll` 和 `Anchor = Right` 不能同时用。**
   容器每布局一次控件就变宽一次（实测从 1361 涨到 2532），右边直接跑出画面。
   解法：只锚左上，宽度由 `Resize` 事件手动算。
3. **`DataGridView` 的 `CurrentRow` ≠ 用户选中。**
   它会在数据绑定后、以及**标签页重新显示时**自动把第一行设为当前行，
   把 `CurrentCell` 设成 null 也挡不住切标签页。
   解法：用独立的 `_connectionSelectionConfirmed` / `_ruleSelectionConfirmed` 标志，
   操作按钮只认这个标志。

另外：**WinForms 的 Label 不解析 Markdown**，别在 Text 里写 `**粗体**`，会原样显示。

### 4.4 ★ 数据与线程（这三条各自对应一次崩溃或诡异行为）

1. **绑定给 `BindingSource` 的 `List<T>` 只创建一次（`readonly`），之后用 `Clear` + `AddRange`
   原地更新，绝不能重新赋值。** 否则 BindingSource 还指着旧列表，表格永远是空的。
2. **顺序必须是：先抓选中项 → 再替换数据 → 最后重绑。**
   反过来的话，列表一旦变短，表格里旧行的索引就越界，
   `CurrentRow.DataBoundItem` 会抛 `IndexOutOfRangeException` **把程序搞崩**。
3. **后台线程不能直接遍历 UI 线程会改的 List。** 先在 UI 线程做快照（`.ToArray()`），
   后台只处理快照里的对象引用。

## 5. ★ 环境相关的坑（本地能跑、CI 跑不了，或反过来）

### 5.1 网络：HTTPS 到 github.com 不通，必须走 SSH over 443

这台机器的网络环境会**按域名干扰 github.com 的 TLS 握手**：

```
Test-NetConnection github.com -Port 443  → 通（TCP 层）
curl https://github.com                  → 退出码 35（SSL 握手失败），0.16 秒被断
git push（HTTPS）                        → Recv failure: Connection was reset
```

**解**：`%USERPROFILE%\.ssh\config` 里已配好把 `github.com` 映射到 `ssh.github.com:443`：

```
Host github.com
    HostName ssh.github.com
    Port 443
    User git
```

remote 也已经是 SSH 形式：`git@github.com:lovercyh/winappguard.git`。
**不要改回 HTTPS**，改了就用不了。

如果哪天 SSH 也不通，还有备选：让代理工具（本机装的是 `Steam++.Accelerator`，
PAC 在 `127.0.0.1:26561`）跑起来，然后给 git 配 `http.proxy`。

### 5.2 PowerShell 5.1 的编码坑（踩过两次）

- **含中文的 `.ps1` 必须存成带 UTF-8 BOM 的格式。**
  Windows PowerShell 5.1 会按 ANSI 解析无 BOM 的 UTF-8 脚本，中文注释会解码错乱，
  **进而导致语法错误、脚本直接跑不起来**。项目里的两个 `.ps1` 都带了 BOM，
  `.gitattributes` 里也把 `*.ps1` 标成了 `-text` 防止被搞坏。
- **不要用 `Get-Content` / `Set-Content` 批量改含中文的 `.cs` 文件** ——
  同样会读乱再写回去，把文件毁掉。要用：
  ```powershell
  [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
  [System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding($false)))
  ```

### 5.3 MSBuild / 发布相关的坑

1. **`dotnet restore`（不带 `-c`）+ `dotnet build -c Release --no-restore` → `NETSDK1047`。**
   因为 `RuntimeIdentifier` 写在 `Condition="'$(Configuration)' == 'Release'"` 里，
   不带 `-c` 的 restore 是按 Debug 还原的，没有 win-x64 的资产。
   **Release 那步不要加 `--no-restore`。**
2. **单独 `dotnet build tools/SelfCheck -c Release`（不带 RID）→ `NETSDK1151`。**
   「自包含的可执行文件不能被非自包含的可执行文件引用」。
   自检工具的 csproj 里在 Release 段声明了和产品一致的 RID / SelfContained 配置。
3. **`app.manifest` 的 XML 注释里不能出现连续两个减号。**
   曾经在注释里写了 `--audit`，清单变成非法 XML，**程序启动报「并行配置不正确」——
   而 MSBuild 不校验这个，构建照样成功**，只在运行时炸。
4. **不要开 `PublishTrimmed`。** WinForms 大量依赖反射和 COM，裁剪后会在运行时才报错。

### 5.4 其他

- **自检工具的清单刻意是 `asInvoker` 而不是 `requireAdministrator`。**
  因为 CI（GitHub runner）无法弹 UAC，如果强制提权，连只读的 `--audit` 都起不来。
  需要管理员权限的模式由程序自己检测并提权（见 `tools/SelfCheck/Program.cs`）。
- **.NET SDK 会把 git 提交号附在版本后面**（形如 `1.1.0+5a7219c22e75…`）。
  这是标准行为且有用（用户报 bug 能定位到提交），状态栏里截成短号显示。
- **单文件 exe 的元数据读不到我们的代码**（它是宿主程序，我们的程序集被打包在里面）。
  所以 `--audit` 审计的是 **`WinAppGuard.dll`**，不是 exe。

## 7. ★ 踩坑清单（最有价值的部分）

### 用户在实际测试中发现的问题（4 个）

1. **阻止程序后无法恢复联网** —— 最初把「允许联网」的入口放在**实时连接列表**里，
   但被阻止的程序连不上网、也就不会出现在列表里。**拦截越成功越无法恢复。**
   修法：把恢复入口挂在**持久化的防火墙规则**上（新增「已阻止的程序」页）。
   **这是最严重的一个，属于设计缺陷，不是代码 bug。**

2. **重复启动出现两个托盘图标** —— 原先只依赖计划任务的 `Instances=IgnoreNew` 策略，
   它只管计划任务触发的启动，**管不住用户手动双击**。
   验收清单里写了「不会出现两个图标」却从没实现过。
   修法：命名互斥体 + 广播窗口消息，第二个实例把已有窗口叫到前台后退出。

3. **「任务详情」文字变长压住了下面的按钮** —— `AutoSize` 标签 + 绝对坐标 + 固定高度容器。
   修法：改 Dock 布局，详情区开 `AutoScroll`。**见 4.3 铁律 1。**

4. **开机自启开启后按钮被挡住**（同上一条的另一个表现）。

### 自测中发现的（6 个）

5. **表格永远是空的** —— `BindingSource.DataSource` 绑的是初始那个空 List，
   而扫描完 `_connections = connections` 换掉了引用。**见 4.4 铁律 1。**
6. **连接数变少时程序崩溃**（`IndexOutOfRangeException`）—— 先替换数据再读表格当前行。
   **见 4.4 铁律 2。**
7. **切一次标签页，安全保护就失效** —— `DataGridView` 会自己选第一行。
   **见 4.3 铁律 3。**
8. **托盘图标糊** —— `new Icon(stream, size)` 只挑「不大于目标尺寸的最大一张」，
   125% DPI 下退到 16×16 再被系统拉伸。修法：把 16/20/24/28/32 全烘焙进 ico。
9. **`AutoScroll` 与 `Anchor=Right` 打架**，控件越排越宽。**见 4.3 铁律 2。**
10. **`notepad.exe` 被误判成「未签名」** —— `WinVerifyTrust` 只查内嵌签名，
    而大量 Windows 系统文件只有目录签名。**见下一条。**

### 开源/CI 阶段发现的（4 个）

11. **CI 的 `NETSDK1047`** —— 见 5.3 第 1 条。
12. **Node 20 弃用警告** —— action 版本太老（checkout v4 → v7 等）。
13. **发布说明被 PowerShell 搞乱** —— 双引号 here-string 会把 markdown 的代码围栏
    （反引号）当转义符。修法：改用**单引号** here-string + 占位符 Replace。
14. **`app.manifest` 的 XML 注释里有 `--`** —— 见 5.3 第 3 条。

### v1.1.0 签名功能本身的坑

15. **只查内嵌签名会漏掉一半** —— Windows 有两套签名机制：

    | 机制 | 位置 | 谁在用 |
    |---|---|---|
    | 内嵌签名 | exe 自己的 PE 证书表 | 第三方软件基本都用这种 |
    | 目录签名 | `C:\Windows\System32\CatRoot\` 的 `.cat` | **大量 Windows 系统文件只有这种** |

    `notepad.exe` / `cmd.exe` / `winver.exe` 都属于第二类。
    验证方法：读 PE 头的**证书表偏移**，为 0 就是没有内嵌签名。

16. **判定顺序有个刻意的取舍**：内嵌签名**存在但验证失败**时，
    **不再去查目录签名**。否则一个签名被篡改的文件，只要恰好被某个目录收录过，
    就会被**洗白成「签名有效」**。

17. **第一版写错了提前返回** —— 「先取签名者名字，取不到就直接判定为未签名」，
    导致所有文件都可能被误判。**权威结论只能来自 `WinVerifyTrust`，名字只是附加信息。**

18. **`X509Certificate.CreateFromSignedFile` 在 .NET 9 起过时且无等价替代品。**
    改用 `WTHelper*` 从 WinVerifyTrust 的验证状态里直接取证书 ——
    不仅去掉了过时 API，目录签名文件的签名者名字也能取到。

### ★ 界面改动必须用「渲染 + 断言」，不能只看一眼

这个项目里**很多界面问题是特定状态下才出现的**，跑起来看一眼发现不了。
已有的做法是写临时 harness：

1. 反射构造窗体 → `form.Show()` → `Application.DoEvents()` 轮询等状态就绪
2. 反射调用**产品真实的私有方法**（如 `OnGridCellMouseDown`、`RebindGrid`），
   不要绕过去自己模拟，否则测的不是真实路径
3. 用 `form.DrawToBitmap()` 存成 PNG，**然后真的去读那个图看**
4. 把关键判断写成断言（控件矩形是否相交、宽度是否越界、颜色是否匹配）
5. 至少覆盖：三种文字长度（短/中/最长）、标签页来回切换、窗口缩放

**已经固化的断言**（改相关代码时会用到）：
主界面状态机 25 项、设置页布局 20 项、加固 21 项、单实例 12 项、
防火墙 42 项、签名颜色优先级 13 项。

## 10. 与项目负责人协作的方式

这些是实际协作下来总结的，照着做能少走很多弯路。

### 工作节奏

- **一次只做一个目标**，做完**停下来**让他验证，不要一口气推好几步。
- 每轮回复的结构他用得比较顺：
  1. 交付物清单（新增/修改了哪些文件，各自干什么）
  2. **实测数据**（不是「应该能行」，是真跑出来的数字）
  3. 需要他做的验证（表格形式，一条一条可勾选）
  4. 下一步
- **他会自己在虚拟机里测**，并且**很擅长找 bug**。不要糊弄 ——
  他没测过的项要如实标注「未验证」。

### 必须主动做的事

- **发现需求冲突或安全风险要立刻提出来，并给出建议方案，等他确认。**
  他明确要求过这一点，而且确实会采纳。
- **踩到坑要写进代码注释说明原因**，不要只是改完就算。
- **自己的推断被实测推翻时要坦白承认**，并把这个教训记进文档。
  项目里已经有几条「我原先以为…实测推翻了」的记录，他认可这种诚实。

### 几个他做过的决定（不要擅自改回去）

- **证书吊销检查默认开启**，接受程序因此产生网络流量 ——
  代价是文档里「不联网」的说法必须改成「自身不含网络代码，但默认会联网查吊销」。
- **行底色用整行染黄**（未签名），不是只标签名格。
- **配色分级**：签名问题=淡红、未签名=淡黄、已阻止=淡蓝；
  优先级「签名问题 > 未签名 > 已阻止」。
- **提交历史一次性提交**，不做按阶段的拆分。
- **代码注释保持中文**，只把 README 写成英文。

### 交付语言

**全部用中文回复。** 技术术语可以保留英文原文。

## 11. 给新接手 AI 的建议开场

如果你是新的 AI 会话，建议先做这几件事再动手：

```powershell
# 1. 确认代码和产物状态
git log --oneline -5
git status
dotnet build WinAppGuard.sln -c Debug -v minimal

# 2. 跑一遍审计，确认基线
.\dist-tools\WinAppGuard.SelfCheck.exe --audit

# 3. 如果要改界面，先把上一次的截图渲染出来看看
#    （不要只看代码就改布局 —— 见 4.3 铁律）
```

然后问他一句：**「这次要做什么？需要我先跑一遍哪部分的验证？」**
